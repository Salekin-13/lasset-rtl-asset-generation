THIS CALL: PHASE 1, CONCEPTUAL ASSETS

For each UNIT of the diagram:

1. Interface. Name information entering or leaving through the unit's INPUTS and OUTPUTS: data received, held or returned; settings and configuration; state and status; commands, requests and responses; events signaled to other modules.

2. Inside. Name state the unit holds that its behavior depends on and no port shows directly: a mode, a lock, a count, a stored setting, a state machine's state. Also name each enable, select, override or lock deciding whether other information is used, passes or may change: such a decision is information of its own. Neither sentence covers sequencing state outside a coprocessor (a rule below).

3. Merge and split. Information that always travels together for the same use, or repeats per index or per port of one role, is one piece. Information with different uses is separate, even on a shared port. An internal signal only timing one step of other information (an increment pulse, a started flag, a one-cycle request) is part of what it times, not its own decision. A compare of stored state with a request, a count with a stored limit, or a written value with a fixed value, whose result picks or triggers what happens next, is its own piece (step 2), even when it lasts one cycle. Hold it where computed; never merge it into its inputs or the action it triggers. Any other compare, decode or gate is judged by step 2 and the timing clause. A tick only pacing a step is a pacing pulse; a compare only picking a computation's result (a minimum or maximum) is a working value.

4. Rubric. Per piece, answer each question "yes" only when both parts hold: first, what the information is, judged from what the RTL does with it; second, a mechanism the RTL shows or the black-box rule (section 1) gives.
   Confidentiality. Assume the IC integrating the IP requires confidentiality protections. Is this information, received as input or generated inside the IP, something an integrator may consider secret? If the first part holds, can an element of the IP leak or expose it by holding or carrying it where the integration level can observe it: an output port, a read-back, a debug or test path, a status depending on it, a shared structure, or data-dependent timing (4.4)? Phase 2 judges authorization, so a designed use never makes the second part "no".
   Integrity. Assume the IC integrating the IP requires integrity protections. Is this information material an integrator may deem sensitive, or a state or configuration setting that must be immutable during certain operations or modes? If the first part holds, can an element of the IP modify it?
   Availability. Does this information gate (enable, block or select) an output port or an input port's use, or would the IP or IC stop working without it? If the first part holds, can an element of the IP block, disable or withhold it, so that a port is blocked, a required transfer is lost, or the IP or IC halts?
   Undermined expected behavior. Does a privileged mode, an override, a bypass, test-packet injection or similar integration-level behavior act on this information? If the first part holds, can that behavior make the IP produce incorrect output, or stop its function, under normal operation? Focus on what may be compromised.

5. Keep. Keep a piece as a conceptual asset when any question is "yes" AND it passes the asset test (2.3); list the rest under "Not Kept". Phase 2 sees only kept concepts, starting from their held lines.

6. Anchor. Under "Enters Through" list each unit port whose value is carried (2.2) into the information; under "Leaves Through", each unit port written by an element carrying it; either may be empty. Skip ports that only decide the information or that it only decides. When a state machine, apart from reset, changes state only at steps a peer device's clock paces, and its next state depends only on its current state and one bit of a non-record input port (directly or through synchronizer stages), that port, never the peer's clock line, is the input port setting the state (2.6), though only conditions test its bit (an implicit flow, 2.2). List that port under "Enters Through" of the concept holding that state; the skip above does not apply to it. Write ports as INPUTS and OUTPUTS do, or as the closed-set field when one field of a record port alone carries the information.

Rules:
- Describe a conceptual asset by what the information is, not an element name. A diagram arrow shows a flow, not an asset.
- Precedence. A rule's bar is its sentence saying information is not a conceptual asset or not a piece of its own. What a rule judges as usual or does not cover is spared only from that rule's bar.
- Clocks and resets. Clock and reset inputs, a reset request the unit only combines, gates, registers or passes to a reset chain or reset output port (its copies and that output port included), and chains only synchronizing or releasing a reset (a reset shift register, a registered reset copy) are not conceptual assets under any question. A serial link's clock line the unit drives to, or senses from, a peer device is not a conceptual asset either, nor is a setting or decision whose only use, apart from a read-back, is to shape that line (polarity, phase against the data, holding it while the peer stretches it), although this rule judges other clock settings as usual. Do not cite their lines as held lines. The link's data and select lines, its rate setting and the unit's clock-enable outputs are judged as usual. A setting's only use is to shape a serial link's clock line also when, apart from its read-back, its counterparts show it gives value to or decides only the element driving that line, and that element gives value to or decides nothing but the line, even where the line's phase sets when the peer samples or sends data. It is then not a piece of its own: keep no concept for it and do not cite its lines as held lines; a transfer-mode, format or rate concept holding other settings stays, without it. Clock-controlling settings or requests (an enable, a rate) are judged as usual, as is a reset-triggering decision (a timeout) where it is computed, not a copy the unit only gates or registers, except as the next sentence says. A decision that a write was refused or carried a wrong value (a write while locked, a wrong password), its gated or registered copies, and a setting choosing only whether such a violation resets are not conceptual assets either when, apart from a read-back, they only request a reset and record its cause, although step 3 makes a compare of a written value with a fixed value a piece. The cause record, the lock refusing the write, and a compare outcome restarting a counter are judged as usual.
- Build-time values. A generic or constant only fixing the build (a feature switch, size or depth, fixed address or address map, buffering choice) is not a conceptual asset: no element of the IP can change or withhold it at run time. Nor is a run-time bit that a statement ANDs with a build-time switch and whose effect includes writing characters to a file or the screen (a simulation-only mode), although a bus write can change it: it is part of that build choice and is not the run-time decision the next sentence asks for. Instead, name the run-time decision using it as its own concept (which port an address selects, which requester is granted).
- Pacing pulses. A tick, edge pulse or divider count made inside the unit only to pace another step, or an input port used only as a condition letting such a tick or count advance, is part of that step or its rate setting (step 3), unless an output port carries the pulse itself (2.2); an output port the pulses only decide or time does not count. Do not name it in any concept's information or cite its lines as held lines. Not pacing pulses: a request held until served, a start pulse decoded from a received command, and a step counter (sequencing state, below, judges a step counter; in a coprocessor, such a count of its busy state is one piece with that state).
- Forwarded transactions. A bus transaction (a request or response with its address, data and handshake) that the unit only forwards between its ports or to a sub-unit, without storing, computing or deciding it, is not a conceptual asset of this unit; this rule, its sentences on relayed data included, never covers a bus whose address this unit drives on a non-record output port of its own and whose acknowledge it takes on a non-record input port of its own (judge from port names which ports are that bus's address, acknowledge and other lines, and say so): the request it drives onto that bus's ports and the response it takes from them are judged as usual, as information leaving and entering the unit there. Also forwarding: merging several ports' bus responses into one (an OR or a multiplexer); a register stage passing a whole request or response record on unchanged a cycle later, although it stores the record; and a record this unit only wires between one of its ports and the port map of an instance of another IP, with no statement of this unit reading or writing it (a constant tied to it in a generate branch lacking the instance is no such statement), even though the black-box rule lets the instance change it. The decision whether or where it passes is judged as usual. Relayed data is data a transfer carries into or out of the unit (data loaded or stored, instruction words fetched, messages received or sent) when no statement of this unit stores it or computes from it: it only moves between a unit port and an instance of another IP, between such instances, or into a statement only mixing it with other values (an OR, a multiplexer). Relayed data, alone or with only the acknowledge and ready lines timing its transfer, is not a piece of its own, even in a unit executing instructions and although step 1 names data received or returned and 4.2 end-user's private data: keep no concept for it. Judged as usual by this rule only: a transfer's address and direction; a wait or fault flag; an interrupt or debug request; a register read-back word, and the register contents an instance holds; an arithmetic, logic or compare result an instance computes from operands; the value a mixing statement writes (such as the value written back to a register); and data the unit stores, shifts through its own register, generates or computes from, even when a buffer instance also holds it. Judge from port names which instance ports carry relayed data and which a computed result, and say so.
- Second copies. An internal register (not a port) that directly copies bits of one other register of its own entity, not as an index, whose other assignments write only constants, and that no condition reads, is a copy kept only while the value moves (2.6). It is not a piece of its own: name its information under the copied register's piece, and do not cite its lines as held lines.
- Bus handshake copies. A bus response acknowledge only repeating or delaying the bus request strobe, and a bus error flag tied to a constant, are not information of their own. In a unit passing bus requests from an input bus request port to an output one, a register of one bit, or one bit per requester, not a request waiting for a grant (a rule below), holds no information of its own when every assignment to it (directly or through its next-value signal), apart from clearing or holding it, copies or ORs in only the strobe, lock bit or response error bit of the access in progress, or sets it when a test reading only that access's fields and build-time values holds (a route bit), and the unit reads it only to start, pass on, route, time or end that access, the access it serves or that locked sequence, or to drop words that access fetched: the register only re-times a value the access already carries. It is not a piece of its own, although steps 1 to 4, Build-time values and 4.4 would name it a request, status, lock, select, compare or bypass, and even where another rule judges a decision or held request as usual. A compare or decode reading a register this rule bars, and otherwise only that access's own fields and build-time values, or used only to set such a register, is part of that register (step 3), not a piece of its own. Keep no concept for them and cite none of their lines as held lines, except a line also assigning an element this rule does not bar. Judged as usual: the grant, its select and strobe; an address decode choosing which of several output bus request ports gets the access; a pending fence or flush clearing what the unit stores; a busy flag set when the unit itself issues an access; a timeout count, its error and its suppression flag; a reservation; a software-set lock guarding later accesses; a read enable deciding whether stored data leaves on the response; and a cache's hit. A one-bit register that one unconditional statement sets on every clock edge to a stored state bit or flag of this unit, copied or inverted and ANDed only with terms saying when it applies (a request strobe, its read or write bit, an operation-type decode), and that only a bus response's acknowledge or data fields read, only re-times that state to the response. It is part of that state, not a piece of its own, although step 1 names status and responses and step 3 makes a compare of stored state with a request a piece: keep no concept for it and do not cite its lines as held lines. Judged as usual: that state, where held; a register set only from the unit's input ports (a read enable from a strobe and a read or write bit); and a flag that a condition sets to a constant (a timeout error raised at a count's limit).
- Working values. Partial results inside a computation (a partial sum, product or round value, a synchronizer stage, a debiasing step) are part of the result they produce (step 3), not concepts of their own. So are the state and flag made inside a debiasing step to choose which raw bits it accepts: although step 2 would call them a decision, they only shape that result, like a compare picking a minimum (step 3). Do not name a synchronizer stage in any concept's information or cite its lines as held lines.
- Slices. A signal (not a port) whose only assignment copies part of one element's bits (a slice), or joins signals each doing so from the same element, only carries that element's value (2.2), unless that element is a bus request or response record port or a field of one: such a slice is judged as usual (2.6). Otherwise it is not a piece of its own: do not cite its lines as held lines.
- Hand-offs. Check each port-map line where an instance's non-record output port drives a signal another instance or this unit's logic reads. A wait, fault or write-enable flag, or an access address, that one instance outputs on a non-record port to another instance or this unit's logic is a hand-off; if the RTL cannot show which it is, judge from the port names at either end and say so; a field of a record an instance outputs is never a hand-off, even wired alone into another instance's non-record port. A hand-off is its own piece (step 2), unless Port buffers covers it (then this rule does not apply). No step-3 clause or other rule folds it, even when it travels with the data it qualifies, when another instance outputs the same address earlier or later (cite each output's port-map line, in one piece), or when it is one bit of a count: then hold it at the line assigning that bit to the instance output, and a count kept only to make it belongs to this piece.
- Decided-on instance outputs. A value that an instance of this file outputs on a non-record port, other than a hand-off, crosses into this unit whole at the unit signal that port drives through the port map when that signal's closed-set entry gets its value from that instance port and lists "decides" partners, because this unit's decisions then use the value only through that signal (2.6, outward: the instance output this unit then uses as the value itself); when that signal lists no "decides" partner, this sentence does not apply. Hold such a value also at the port-map line wiring that port to that signal (unless the Port buffers rule bars citing that signal's lines), besides any line where the instance computes it; this rule sets only where the piece is held, not whether it is kept.
- Held outcomes, addresses and settings. Where an accepted compare outcome, an access address or an operand setting is held: the outcome of a compare of a written value with a fixed value is held at the register that the branch taken when the value matches sets, as that register is where the compare is computed (step 3) even when it keeps the outcome for one cycle only and only restarts a counter, so it is neither the action the compare triggers nor a one-cycle request folded into what it times, and the line where the other branch requests a reset is never its held line; an access address that leaves the unit in the address field of a bus request record port, which never holds it (2.6), is also held at each non-record port on which an instance of another IP outputs that address to another instance, judged from the port names at either end (an address output, or an output wired into an address input) as a hand-off; and a setting decoded from instruction fields that changes how operands are read (signedness), not a flag only naming the operation, is held at the lines assigning it, even inside a concept about the operation it belongs to; Phase 1 cites each such line as a held line of the concept whose information it is, and Phase 2, at the block owning each such line, names the element the line assigns, even when no arrow it follows lists that element, and labels it primary for that concept.
- Instance-driven records. A record driven whole by one instance of another IP and wired whole into one or more other instances' port maps (decoded controls or fetch results between sub-units; closed set: the record's own entry gets its value from one instance port and gives it only to instance ports) holds nothing of this unit, even if a port map also takes a field alone, a statement of this unit reads one, or it carries the instructions this unit executes: that instance holds each value; the record and its fields, one-bit flags included, only carry copies, and none is a non-record signal. So information such a record or its fields carry, and that no other element except bus request or response record ports stores, computes or passes whole across the boundary (2.6; an instance output carrying it only by the black-box rule does not count), is not a piece of this unit, although step 2 names a state machine's state and each enable, and 2.4 and 4.2 the privilege mode and program counter: keep no concept for it. Information a non-record unit input port itself brings in crosses the boundary whole at that port (2.6), even when the port is wired straight into that instance: list the port under "Enters Through" and hold the information at the line wiring the port. An element this unit's statements compute from such a field and other values keeps no concept about that field alive. Cite no declaration or port-map line of such a record or its fields as a held line. Judged as usual: non-record signals handed between instances; non-record unit ports, even one wired straight into an instance (a debug or interrupt request line); records this unit's statements set, whole or per field; records whose fields port maps or several instances set separately; and, for its other values, an element this unit's statements compute from such a field and other values.
- Register read-back. In a unit executing instructions, the word an instance outputs for reads of its control and status registers, when a statement of this unit merges it directly into the value written back to a register, is its own piece: those registers' contents as software reads them. Hold it at that instance output; no step-3 clause or other rule folds it. In a unit executing instructions, a word that an instance outputs for reads of its own control and status registers, and that this unit reads only in an OR into the word another instance takes in to answer such reads, only carries those registers to the other instance's read-back: the registers (a count, a protection setting, a configuration or status bit) stay inside the first instance, and no statement of this unit stores, computes or decides them (a constant tied to the word in a generate branch lacking that instance is no such statement). So these words (that word and the one the OR makes) and those registers are not pieces of their own, although step 2 names a count and a stored setting and 2.4 a memory-protection configuration: keep no concept for them, as the read-back piece covers those registers as software reads them; cite no line of these words as a held line, nor, for the read-back piece, a port-map line feeding the first instance. Judge from port names (section 1's second exception) which outputs and inputs this rule names, and say so. Judged as usual: the read-back's instance output, the value written back to a register, and the first instance's other outputs (a wait or fault flag, a result, an access address, a unit output port it drives), even when computed from those registers.
- Port buffers. A FIFO instance whose write data is a unit input port's value (a bus write, or bits shifted in from a serial input port) only buffers data between two ports. Its fill flags (holds data, has room), push and pop strobes, a command only clearing it, and a flag recording a push while full (even a register of this unit) only time, gate, clear or report on that data: they are not pieces of their own, although step 2 would call some a decision. Judged as usual: the buffered data, an output port these flags decide (an interrupt request, a ready-to-receive line), and a unit enable that also clears the FIFO. A FIFO holding data the unit generates itself (random bits) is not covered: its holds-data flag that a statement of this unit tests to return either that data or something else (the flag withholds the data) and a register whose only use is to clear that FIFO (it discards the data) are each their own piece (step 2) that no step-3 clause folds into that data, the flag held at the line wiring it out of the FIFO, with the read-data line returning the flag as its exit (step 6), and the register held at the line assigning it, while its other flags and its push, pop and enable controls are judged as usual. Any FIFO instance, whatever data it holds, keeps each word only while the word moves (2.6: a copy kept only while the value moves), so the signal wired to its write-data input and the signal its read-data output drives only carry the word; the buffered data is judged where the unit generates it (random bits) or where it crosses the unit's boundary. Keep the buffered data as a piece, but cite no line assigning or wiring those two signals as a held line; leave "Held Lines" empty if no other line holds the data. Judge from port names that an instance is a FIFO, which outputs are its flags and which ports carry its data, and say so.
- Sequencing state. Outside a coprocessor, a unit shifting in bits it generates, and a test or debug access port that a peer's clock paces, a state machine's state register (not a flag a request or command sets, held until that request is answered; a reservation one access sets and a later one checks; or the current grant, a state naming which requester holds a shared path, with the select and strobe it drives) or a bit, phase, word or step counter (not a count whose compare with a limit raises a reset, error or interrupt, or sets an output level, such as a timeout or timer count, nor that compare's flag or a timeout's suppression flag) that restarts with each transfer or operation the unit performs (even if one bit copies an enable or a queued command picks the first step), and is read only to pick that transfer's next step, to time or gate its strobes, commands, shifts, loads, acknowledges and multiplexers, or to point its address at the next word, is sequencing state: it only orders steps of information other elements hold, so neither it, an internal busy flag decoded from it, nor an internal done flag it sets at its last step is information of its own, while any unit port (even an interrupt request these flags decide), the enable and rate settings, other elements its steps load or drive (a chip-select register, an address), and an instance output port assigned one of its bits (a hand-off when another instance reads it) are judged as usual, and so is a peer's command: when a non-record unit input port (never a clock, a reset or a serial link's clock line) reaches the unit's logic only through synchronizer stages (registers only shifting that port's bit along, and wires only copying one of their bits) that give value to nothing but each other and decide nothing but a state machine's state register, and no conceptual asset holds that state, the port's bit is that peer's command to the state machine, information of its own that enters through that port, whose primary is that port (2.6: the input port setting it), never that state register, which the bit only decides (2.2), nor those stages. Sequencing state and its internal busy and done flags are not pieces of their own, although step 2 names a state machine's state, a count and a select, and 2.4 control flow (a program's): keep no concept for them, and cite none of their lines as held lines, except one also assigning an element this rule does not bar. In a coprocessor, a count that a multi-cycle operation steps every clock cycle of its busy state, and whose end test only leaves that state, is a step counter, one piece of information with that state. Keep that state as a concept and hold the count in it, not in the operation's result or its pacing.
- Serial shift registers. In a unit shifting data bit by bit onto or off a serial data port, paced by the unit's own rate setting, the data shift register only holds each word while moving it between that port and the element taking or giving the whole word, so the port is where that data crosses the unit's boundary whole (2.6). Keep the data as a piece: list that port under "Enters Through" or "Leaves Through" and cite the lines reading or driving it as entry or exit lines, even when they name the shift register; cite no line assigning the shift register as a held line, and leave "Held Lines" empty if no other line holds the data.
- Buffer and engine status bits. A status bit a bus read returns is not information of its own when every element it copies (even inverted) or combines is barred by this call's rule on a FIFO only buffering data between two ports (never a flag of a FIFO holding data the unit generates itself) or on sequencing state: it only tells software whether the buffered or shifted data can move or was lost, which that data, its settings and the output ports these elements decide already cover. Although step 1 names status and 4.3 status signals, keep no concept for such bits, alone or grouped as the status software reads, and cite no read-data line returning them as a held line. Not covered: a bit returning anything else, even in the same read word (a stored setting, selection or lock, a reset's cause record); it belongs to the piece it returns, as that piece's exit (step 6). Not covered either: the output ports these elements decide (an interrupt request, a ready-to-receive line), a register a test or debug access port shifts out, and, in a unit executing instructions, the word an instance outputs for reads of its control and status registers.
- Port options. A setting a bus write stores is a port option when, apart from its read-back, its counterparts show it gives value to or decides some element, and each is an interrupt request output (it picks which events raise it), a flow-control handshake output, or an element decided at a test letting a flow-control handshake input (or its synchronized copy) hold a transfer: it only tunes those ports, which carry the outcome. Judge from port names which ports are interrupt requests or flow-control handshakes, never a serial link's clock line, and say so. Judged as usual: those ports, and a setting with another such element (an enable also copied into engine state, clearing a buffer or driving a clock-enable output; a rate setting; a lock; a limit compared with a count). A port option is not a piece of its own, although step 2 names each enable, step 3 splits by use and it gates an output port: keep no concept for it, name it in no concept's information, and cite no line assigning it as a held line. A concept also holding a port it tunes stays, for that port alone.
- Cached copies. In a cache (a unit answering a read from its own copy when a stored tag matches the address, else fetching the words over a backing bus), the copied words copy backing-memory data, and the tag and valid bits only record which words are copied: none is a piece of this unit, although steps 1 and 2 would name them and 4.4 names caches. Judged as usual: its decisions (the hit, the bytes a write changes, the address, its fill, clear and invalidate commands, a pending fence or flush), and a memory that is itself the store.
- Held addresses. A register whose value, apart from constants and itself, comes only from part of an access's address field, directly or through its next-value wire (a wire giving value to or deciding nothing but that register) or a wire only copying that part, and that only feeds other addresses or indexes a memory, holds that address only while the access is served (2.6: a copy kept only while the value moves). It and its next-value wire (not a wire only copying that part and also giving value to or deciding another element: that wire is the address's own element, judged as usual) are part of the access address, not pieces of their own: do not cite their lines as held lines.
- Memory access address. In a unit that is itself the store of a memory (an array it assigns on a clock edge, not a cache's copies), a wire whose only assignment copies or slices the address field of a bus request record port (closed set: role "index", and that field is its only "gets value from" partner) and whose value picks which word of that array an access writes or reads is a select (step 2) deciding which stored word the access uses or changes, so it is a piece of its own, the access address, even though the unit returns it on no output port and holds it in no register, and although Access command fields lists register-select address bits and byte enables, step 3 would merge it into the stored words or the access, and 2.2 calls its use an index flow (that flow carries the address into the word read; it does not make the address only a path to the stored words): a changed address makes the access write or return a word it was not aimed at, so judge its rubric by that mechanism, and hold it at the line assigning it (not its registered copy, which Held addresses bars).
- Operation selectors. In a unit executing an instruction or atomic memory operation a processor issues to it (a coprocessor, an atomic read-modify-write), instruction or request fields only picking the operation or the result form returned (an opcode, a function code, an instruction-type bit), their stored copies, and flags decoded from them only naming the operation are part of that operation (step 3), not pieces of their own, although step 2 names a select. Do not list them under "Enters Through" or cite their lines as held lines, except a line assigning an element this rule judges as usual. Judged as usual: a start command or pulse, even one decoded per operation (a multiply or divide start), a register access's address and write enable, a completion flag, and a setting decoded from them that changes how operands are read (signedness). A plain bus read or write is not covered: on a record port, Access command fields judges its read or write bit and a read enable made from it. In a unit executing an instruction or atomic memory operation a processor issues to it, a register whose value, apart from constants and itself, comes only from one source operand input (a port or a request-record field) when the operation starts, directly or through its next-value wire, and reaches an output port only through the element holding the result, only holds that operand while the operation uses it (2.6: a copy kept only while the value moves). It and its next-value wire are part of that operand's piece: keep that piece, list the operand input under "Enters Through", cite the lines where it takes the operand as entry lines, and do not cite them as held lines.
- Access command fields. On a record port (never on non-record ports, even ones together carrying an access) carrying accesses addressing this unit's own registers, FIFOs, locks or memory words (not a cache's copies), the fields only saying whether an access happens, its direction and which register, FIFO or bytes it reaches (a strobe, a read or write bit, register-select address bits, byte enables; an address indexing a memory's stored words is the access address, not one of them), and a write enable whose assignment reads only these fields and that only lets a register take the written data, are part of the information the access writes or reads, not information of their own. They are not pieces of their own, although steps 1 and 2, Build-time values and Per-region checks would keep some: keep no concept for them; cite no line only testing them, or only assigning such a write enable, as a held line. A signal of its own decoded from these fields that gates or masks what a read returns (a read enable, a select also masking read data), or pops a FIFO of data the unit generates itself, is its own piece (step 2): name it by what it decides and hold it at the line assigning it; no step-3 clause folds it. An inline condition is no such signal, nor is a strobe of a FIFO that Port buffers covers. Such a field whose value a register takes as its new content belongs to that register's piece. Not covered: a request held until served, a select routing it on, and a strobe driven on to a unit output port; an operation's start pulse.
- Per-region checks. When the unit makes the same compare or permission check per region or entry and only combines the results (a priority chain, an OR) into one decision, that decision is the piece, held where they combine; the per-region results are its working values (step 3), although step 3 makes a compare of stored state with a request a piece. A per-entry result itself picking where a request goes or which entry an access changes (which port an address selects, which lock is addressed) stays its own piece.
- Arbitration bookkeeping. A register only remembering the previous grant for round-robin priority (not the current grant, its select and strobe, or a request held until served) holds no decision of its own: it only tilts the next grant. It is not a piece of its own, although step 2 names a select: keep no concept for it, nor cite its lines as held lines.
- Requests waiting for a grant.
