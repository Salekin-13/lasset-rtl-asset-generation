THIS CALL: PHASE 1, CONCEPTUAL ASSETS

For each UNIT of the diagram:

1. Interface. Name information entering or leaving through the unit's INPUTS and OUTPUTS: data received, held or returned; settings and configuration; state and status; commands, requests and responses; events signaled to other modules.

2. Inside. Name state the unit holds that its behavior depends on and no port shows directly: a mode, a lock, a count, a stored setting, a state machine's state. Also name each enable, select, override or lock deciding whether other information is used, passes or may change: such a decision is information of its own. Neither sentence covers sequencing state outside a coprocessor (a rule below).

3. Merge and split. Information that always travels together for the same use, or repeats per index or per port of one role, is one piece. Information with different uses is separate, even on a shared port. An internal signal only timing one step of other information (an increment pulse, a started flag, a one-cycle request) is part of what it times, not its own decision. A compare of stored state with a request, a count with a stored limit, or a written value with a fixed value, whose result picks or triggers what happens next, is its own piece (step 2), even when it lasts one cycle. Hold it where computed; never merge it into its inputs or the action it triggers. Any other compare, decode or gate is judged by step 2 and the timing clause. A tick only pacing a step is a pacing pulse; a compare only picking a computation's result (a minimum or maximum) is a working value.

4. Rubric. Per piece, answer each question "yes" only when both parts hold: first, what the information is, judged from what the RTL does with it; second, a mechanism the RTL shows or the black-box rule (section 1) gives.
   Confidentiality. Assume the IC integrating the IP requires confidentiality protections. Is this information, received as input or generated inside the IP, something an integrator may consider secret? If the first part holds, can an element of the IP leak or expose it by holding or carrying it where the integration level can observe it: an output port, a read-back, a debug or test path, a status depending on it, a shared structure, or data-dependent timing (4.4)? Phase 2 judges authorization, so a designed use never makes the second part "no".
   Integrity. Assume the IC integrating the IP requires integrity protections. Is this information material an integrator may deem sensitive, or a state or configuration setting that must be immutable during certain operations or modes? If the first part holds, can an element of the IP modify it?
   Availability. Does this information gate (enable, block or select) an output port or an input port's use, or would the IP or IC stop working without it? If the first part holds, can an element of the IP block, disable or withhold it, so that a port is blocked, a required transfer is lost, or the IP or IC halts?
   Undermined expected behavior. Does a privileged mode, an override, a bypass, test-packet injection or similar integration-level behavior act on this information? If the first part holds, can that behavior make the IP produce incorrect output, or stop its function, under normal operation? Focus on what may be compromised.

5. Keep. Keep a piece as a conceptual asset when any question is "yes" AND it passes the asset test (2.3); list the rest under "Not Kept". Phase 2 sees only kept concepts, starting from their held lines.

6. Anchor. Under "Enters Through" list each unit port whose value is carried (2.2) into the information; under "Leaves Through", each unit port written by an element carrying it; either may be empty. Skip ports that only decide the information or that it only decides. When a state machine, apart from reset, changes state only at steps a peer device's clock paces, and its next state depends only on its current state and one bit of a non-record input port (directly or through synchronizer stages), that port, never the peer's clock line, is the input port setting the state (2.6), though only conditions test its bit (an implicit flow, 2.2). List that port under "Enters Through" of the concept holding that state; the skip above does not apply to it. Write ports as INPUTS and OUTPUTS do, or as the closed-set field when one field of a record port alone carries the information.

Rules:
- Describe a conceptual asset by what the information is, not an element name. A diagram arrow shows a flow, not an asset.
- Precedence. A rule's bar is its sentence saying information is not a conceptual asset or not a piece of its own. What a rule judges as usual or does not cover is spared only from that rule's bar.
- Reading a rule. Check its scope, then each criterion, then each exception it lists, in that order, against the RTL; where a criterion says "only", "every" or "one element", check every assignment or use, not one. Its outcome follows only for an element in scope that meets every criterion (one, where marked "any of") and that no listed exception covers.
- Background on the language (general notes; they decide nothing in this task).
  - The language in outline. VHDL is a hardware description language that has been standardised by the institute of electrical and electronics engineers. A description is made of design units that are analysed, stored in a library, and later elaborated into a model that can be simulated or given to a synthesis tool. The language is strongly typed, identifiers are not case sensitive, and statements end with semicolons. A comment starts with a pair of hyphens and runs to the end of the line. Several revisions of the standard exist, and each added features while keeping most older descriptions valid.
  - Design units. A design unit is the smallest piece of text that can be analysed on its own. The kinds are the entity declaration, the architecture body, the package declaration, the package body, and the configuration declaration. Each analysed unit is placed in a library, which is a named place where the tool stores results. A unit refers to earlier units by naming the library and the unit inside it. Because analysis follows dependence, a unit that is referred to has to be analysed before the unit that refers to it, and tools report an error when the order is wrong.
  - Library and use clauses. A library clause makes a library visible by name. A use clause then makes chosen declarations from a package directly visible, so that they can be written without a long prefix. A use clause can name one item or every item of a package. Two libraries are visible without being named: the library holding the standard package, and the working library, which is the library that receives the unit being compiled at that moment and is referred to by the name work. Context clauses are written before the design unit they apply to, and they cover only that unit and the units that belong to it.
  - Standard packages. The standard package defines the basic types, such as boolean, bit, character, integer, real, time, and string, along with their operators. The standard logic package defines a nine-valued logic type and a vector form of it. The numeric package defines signed and unsigned vector types, built as arrays of the logic type, together with arithmetic, comparison, shift, and conversion functions for them. Older vendor packages once offered arithmetic on plain logic vectors, but they are not part of the standard, and loading them together with the numeric package in one unit can cause ambiguity between overloaded operators.
  - Entities. An entity declaration describes the outside of a design block: its name, its generics, and its ports. It says nothing about how the block works inside. An entity may also contain declarations and passive statements, such as assertions, that are shared by every architecture of that entity. One entity can have several architectures, each describing a different way of building the same interface. The choice among them is made when the design is elaborated, normally through a configuration or, by default, by taking the architecture that was analysed last.
  - Architectures. An architecture body describes the inside of an entity. It has a declarative part, where signals, constants, types, components, functions, and procedures are declared, and a statement part between the begin and end keywords. Every statement in the statement part is concurrent: it exists for the whole simulation and runs whenever something it depends on changes. The architecture sees the generics and ports of its entity as if they were declared in its own declarative part. An architecture may be written in a behavioural, dataflow, or structural style, and the styles may be mixed freely.
  - Ports and modes. A port is a channel of communication between a block and its surroundings. Each port has a name, a mode, and a type, and inside the architecture it behaves as a signal. The mode in means that the block can read the value but cannot drive it. The mode out means that the block drives the value. The mode inout allows both reading and driving, and the mode buffer allows driving from a single source while also allowing the value to be read. The mode linkage exists for completeness and is rarely used.
  - Signals. A signal models a wire or a storage element that connects parts of a design. Its value changes over simulated time, and it holds the list of values scheduled for it, which is called a driver. A signal is declared in an architecture, a package, or a block, or it appears as a port. Assigning to a signal with the less-than-or-equal symbol does not change its value at once. The new value is scheduled for a later moment, and the signal keeps its old value until the simulator performs its update step.
  - Variables. A variable holds a value that is local to a process or a subprogram. Assignment uses the colon-equals symbol and takes effect at once, so the next statement in the same sequence sees the new value. A variable declared in a process keeps its value from one activation of the process to the next, while a variable declared in a subprogram is created afresh each time that subprogram is called. Variables are not visible outside the region that declares them, apart from the shared form, which several processes can reach and which needs care in simulation.
  - Signals compared with variables. The central difference between a signal and a variable is when an assignment takes effect. A signal assignment is scheduled and becomes visible after the current round of process execution ends. A variable assignment is visible at once. For that reason, reading a signal after assigning it within the same process still gives the old value, while reading a variable after assigning it gives the new one. Signals can connect different processes and blocks, whereas variables are private to the region that declares them. Synthesis tools can turn either kind of object into wires or registers, depending on how it is read and written.
  - Process statements. A process is a concurrent statement whose body is a list of sequential statements. When simulation begins, every process runs once until it reaches a wait statement or the end of its list, where it suspends. It resumes when the condition of its wait is met. A process behaves as an endless loop: after the last statement it returns to the first. A process may have a declarative part for local variables, constants, types, and subprograms. Processes in one architecture run in parallel as far as simulated time is concerned, although a simulator executes them one after another.
  - Sensitivity lists. A sensitivity list is a shorthand attached to a process header. It names the signals whose events cause the process to resume. A process with a sensitivity list behaves as if a wait statement on the same signals were placed as its last statement, and such a process may not contain wait statements of its own. A later revision lets the keyword all stand for every signal read in the process, which avoids lists that are incomplete. Where a list leaves out a signal that the process reads, simulation and synthesis can disagree, because synthesis tools often build logic as if the list were complete.
  - Wait statements. A wait statement has three optional parts: an on clause naming signals, an until clause with a condition, and a for clause with a time. The process suspends until a named signal has an event, the condition becomes true, or the time elapses, whichever comes first. A wait with no clauses suspends the process for the rest of the simulation, which is a usual way to end a stimulus process in a testbench. A wait until a condition is evaluated each time one of the signals in that condition has an event.
  - The simulation cycle. Simulation proceeds in cycles. In each cycle the simulator advances time to the next moment at which something is scheduled, updates every signal that has a value scheduled for that moment, and resumes every process that waits on a signal that just had an event. Those processes execute until they suspend, and the values they schedule are placed in the queue. A value scheduled with no delay is placed at the same simulated moment, but in a later cycle.
  - Delta cycles. A cycle that occurs at the same simulated time as the cycle before it is called a delta cycle. A delta cycle has no duration, and delta cycles are how the language orders events that happen at the same instant. A chain of concurrent assignments, each reading the output of the one before, takes one delta cycle per link. The simulator goes on until no events remain for the current moment, and only then does time advance. A loop of assignments that never settles can hold time still, and most simulators stop after a very large number of delta cycles.
  - Concurrent statements. The statements that can appear in an architecture body are concurrent statements. They include processes, concurrent signal assignments, concurrent assertions, concurrent procedure calls, component instantiations, block statements, and generate statements. Their textual order has no effect on behaviour. Each is sensitive to the signals it reads, and runs again when one of those signals has an event. Every concurrent form other than the process is defined as shorthand for an equivalent process, which explains how a simulator treats it.
  - Concurrent assignment forms. A concurrent signal assignment can be simple, conditional, or selected. A simple one assigns an expression to a target. A conditional one lists alternatives with conditions, using the keywords when and else, and takes the first alternative whose condition holds. A selected one begins with the keyword with, names an expression, and lists choices after the keyword select; the choices have to cover every value of the expression. Each form is equal in meaning to a process containing an if statement or a case statement, and each can drive its target with a delay.
  - Sequential statements. Inside a process or a subprogram, only sequential statements are allowed. They run in the order written. The set includes signal and variable assignments and the if, case, loop, next, exit, wait, return, null, assertion, report, and procedure call statements. Later revisions also allow the conditional and selected forms of assignment inside processes. The order of a sequence affects variables directly. For signals it only decides which of several scheduled values is the last, because the last assignment to a signal within one activation replaces the earlier ones.
  - If statements. An if statement tests a Boolean condition and runs one of several branches. It can have any number of elsif branches and an optional else branch. The conditions are tested in order, and the first true one wins. If no branch applies and there is no else branch, nothing executes. When an if statement assigns a signal and some paths leave the signal untouched, the signal keeps its earlier value, and a synthesis tool builds a memory element for it. Conditions are of Boolean type, so a comparison is written when a logic value is tested in the older revisions.
  - Case statements. A case statement selects among alternatives according to the value of an expression. Each alternative lists one or more choices, and the choices together have to cover every possible value of the expression, which is usually done with an others choice at the end. Choices may not overlap. The expression has a discrete type or is a one-dimensional array of characters. For a logic vector, the choices are written out even for values that never occur in practice, because each element has nine possible values, and a later revision adds a matching form that treats the don't care value as a wildcard.
  - Loop statements. Loop statements repeat a group of sequential statements. A for loop runs over a discrete range, and its loop parameter is a constant that exists only inside the loop and needs no declaration. A while loop runs as long as its condition holds. A plain loop with no scheme runs until an exit statement ends it. In a model for simulation, the bounds can be known only at run time. In a model for synthesis, a loop is unrolled, so its range is known when the design is elaborated.
  - Generics. A generic is a constant interface item whose value is given from outside when the block is instantiated. It lets one description serve many configurations, for example different widths or depths, or options turned on and off. Generics are declared in the generic clause of an entity, before the ports, and can have default values. They are visible in the port clause, so port widths may depend on them. They are static, which means their values are fixed at elaboration and cannot change during simulation. A generic map supplies the values when the block is instantiated, and a generic without a default value has to be given one there.
  - Scalar types. The language is strongly typed, so values of different types cannot be mixed without an explicit conversion. Scalar types are the integer types, the floating-point types, the enumeration types, and the physical types. An integer type is defined by a range. An enumeration type lists named values, and it is the usual way to describe the states of a state machine. A physical type has units, as the time type does, which counts in units such as nanoseconds. Each type has its own operators, and the compiler rejects an operator applied to operands of a type for which it is not defined.
  - Subtypes. A subtype is a type with a constraint, or a name for a constrained form of an existing type. A value of a subtype is still a value of the base type, so mixing the two needs no conversion. The constraint is checked when a value is assigned, and a violation stops the simulation with an error. Subtypes make a description easier to read, since a name can express the purpose of a range. A subtype may also add a resolution function to an unresolved type, which is how the resolved logic type is built from the unresolved one.
  - Arrays. An array is a collection of elements of one type, indexed by a discrete range. A constrained array has fixed bounds. An unconstrained array leaves the bounds open until an object of that type is declared or a subprogram parameter is associated. The range can ascend or descend, written with the keywords to and downto. Arrays can have more than one dimension, and there can be arrays of arrays and arrays of records. A slice picks a contiguous part of a one-dimensional array, and concatenation with the ampersand joins arrays or elements into a longer array.
  - Records. A record groups elements of different types under one name. Each element is a named field. A field is reached with a dot, and a whole record can be assigned in one statement or compared for equality. Records are common in interfaces, where they bundle related information so that a long list of ports becomes a single port. A record may contain arrays and other records. The fields of a record signal can be driven from different processes, but a single field cannot be driven from more than one process unless its type is resolved.
  - Type conversion. Because the language is strongly typed, moving a value between types needs a conversion. Closely related types, such as two array types with the same element type and matching index types, allow a type conversion written like a function call with the target type name. Unrelated types need a conversion function. The numeric package provides functions to convert between integers and the signed and unsigned vector types, and to change the width of a vector. A logic vector has no numeric meaning by itself, so it is read as signed or unsigned before arithmetic is applied to it.
  - Resolution functions. A resolved signal may have more than one driver. A resolution function takes the array of all current driver values and returns the single value that the signal takes. The function is attached to a subtype, and any signal of that subtype is resolved. For the standard logic type, the function consults a table: when drivers disagree between forcing values the result is unknown, and a forcing value overrides a weak one. A high-impedance driver gives way to any other driver. A signal of an unresolved type may have one driver only, and a second driver is an error.
  - Standard logic values. The standard logic type has nine values: uninitialised, unknown, forcing zero, forcing one, high impedance, weak unknown, weak zero, weak one, and don't care. A signal of this type starts as uninitialised unless a value is given, which is why signals that nothing has driven show that value at the start of a simulation. The forcing values model a driven line, the weak values model pull-up and pull-down behaviour, and high impedance models a released bus. Only some of the values map to hardware; the rest exist to make simulation results readable.
  - Attributes. An attribute gives information about a named item. Predefined attributes are written as a name, an apostrophe, and the attribute designator. Attributes of types and arrays include the left and right bounds, the low and high bounds, the length, and the range. They let code adapt to the size of an object without naming the size. Attributes of signals include the event flag, which is true when the signal changed in the current cycle, the active flag, the last value, and the time since the last event. Delayed, stable, and quiet are attributes that create new signals derived from an existing one. Users can also declare attributes of their own, which simulation ignores and which synthesis tools may read for vendor-defined purposes.
  - Components. A component declaration describes the interface of a block that is instantiated elsewhere, and it repeats the generics and ports of the entity it stands for. A component instantiation gives an instance name followed by a colon, then the component name, and then maps generics and ports. When a component is used, the tool looks for an entity with a matching interface and binds it, either by default or through a configuration. Declaring components is a long-standing habit, but later revisions let an architecture instantiate an entity directly, which saves the repeated declaration.
  - Port maps. A port map associates the formal ports of a block with actual signals or expressions in the surrounding architecture. Association by position lists the actuals in the order of the formals. Association by name pairs each formal with an actual using the arrow symbol, in any order, and it is easier to read and safer when interfaces change. A formal may be left unconnected with the keyword open, though an input without a default value cannot be left open. An actual for an input may be an expression or a constant, and a formal that is an array or a record may be associated in parts.
  - Generate statements. A generate statement creates concurrent statements during elaboration. A for-generate repeats its contents over a range, producing a set of similar instances or processes, each with its own value of the generate parameter. An if-generate includes its contents only when a static condition holds, which lets a generic switch optional hardware on or off. Later revisions add a case-generate. A generate statement has a name in front of it and may have a declarative part, and signals declared inside are local to each copy created. The conditions and ranges are static, because the number of copies is fixed before simulation starts.
  - Packages. A package collects declarations that several design units can share: types, subtypes, constants, components, functions, procedures, and attributes. The package declaration lists what is visible to its users. The package body supplies the implementations of the subprograms and the values of deferred constants. Splitting the two means that a change to a body does not force recompilation of units that use only the declaration. Later revisions also allow a package to take generics, and such a package is instantiated with particular generic values.
  - Functions. A function computes and returns one value. Its parameters are inputs, and they are constants unless declared otherwise. A function body contains sequential statements and local declarations, and it ends its work with a return statement. A call to a function is part of an expression and is replaced by its result. Functions are either pure or impure. A pure function gives the same result for the same arguments and has no side effects. An impure function may read signals declared outside it or change state, so its result can vary between calls with the same arguments.
  - Procedures. A procedure performs actions and may hand back values through its parameters. Parameters can have the modes in, out, and inout and the classes constant, variable, and signal. A procedure called from a process can contain wait statements, which makes procedures useful in testbenches for bus transactions that span time. A procedure that assigns to a signal parameter does so on behalf of the calling process. A concurrent procedure call is a shorthand for a process that calls the procedure and waits for changes on its input signals. Subprograms can be overloaded and can call themselves, and parameters can have default values.
  - Assertions and reports. An assertion checks a Boolean condition and reports a message if the condition is false. A severity level can be attached: note, warning, error, or failure. The simulator can be set to stop at a chosen level. A report statement prints a message without a condition. Assertions can be sequential, inside a process, or concurrent, in an architecture, where they are checked whenever the signals in the condition change. They are widely used in testbenches to compare results with expected values, and synthesis tools ignore them.
  - Testbenches. A testbench is a design unit whose purpose is to exercise another design unit in simulation. Its entity usually has no ports and no generics. Its architecture declares signals to connect to the block under test, instantiates the block, and adds processes that drive inputs and examine outputs. Because it never has to be built in hardware, a testbench can use the full language, including file access, access types, wait statements, and delays. Testbenches range from a few lines of stimulus to layered environments with generators, checkers, and scoreboards.
  - Clocks and stimulus. A clock is typically produced by a concurrent assignment that inverts a signal after a half period, or by a process that toggles it after a wait for a time. Stimulus is produced by a process that applies values, waits for time to pass or for a clock edge, and then applies the next values. A common way to end a simulation is to stop the clock process once a flag is set, so that no events remain and the simulator ends the run. Later revisions provide procedures that end the run explicitly. A reset is typically applied at the start for a while and then released.
  - Synthesis and simulation subsets. The language was designed for simulation and documentation first, and synthesis later adopted a subset of it. A synthesis tool reads the description and builds logic from it, so it accepts only constructs that map to hardware. Delays, file operations, access types, and waits on arbitrary conditions are typically ignored or rejected. Initial values on signals may or may not be honoured, depending on the target technology. Simulation accepts everything legal in the language, so a model can run correctly and still fail to synthesise, or synthesise to something that behaves differently from the simulated model.
  - Inference. Synthesis tools recognise patterns. A process that is sensitive to a clock edge and assigns signals inside an if statement testing for that edge becomes a bank of flip-flops. A process without an edge test, in which a signal is not assigned on every path, becomes a latch. A process in which every output is assigned on every path becomes combinational logic. Arrays that are read and written in a way that matches a block memory of the target are turned into memory. These patterns are conventions among tools rather than parts of the language standard, and each vendor documents its own.
  - Edge detection and reset. A rising edge is commonly detected with the rising-edge function, or with the event attribute combined with a test of the new level. The function form tests that the previous value was low and the new value is high, so a change from the unknown value to the high value is not counted as an edge. A falling edge has a corresponding function. A reset can be asynchronous, tested before the edge in the same if statement, or synchronous, tested only after the edge. Both are accepted by synthesis tools, though a target library may offer flip-flops of one kind only.
  - Elaboration. Elaboration is the step between analysis and simulation. The tool starts from the top-level design unit, evaluates generics, creates the objects declared in each region, expands generate statements, creates the instances of components and entities, and binds them. It also creates the drivers of each signal and the processes. After elaboration the hierarchy of the design is fixed, and nothing is created or removed during simulation, apart from objects allocated through access types. Initialisation then sets every signal to its initial value and runs every process once.
  - Naming and layout. Style varies between teams, but several habits are common. Names are made from lowercase words joined by underscores, and a prefix or suffix is often used to show the active level or the clock domain. Keywords are written consistently in lowercase or in uppercase. Indentation follows the nesting of statements, and the keywords that begin and end a construct are lined up. One statement is written per line, and long port lists and maps are written one association per line. Comments explain intent rather than repeat the code.
  - Process templates. A clocked process commonly contains a single edge test with an optional reset branch, and assigns all registered signals inside it. A combinational process lists all its inputs and assigns every output on every path, often by giving each output a default value at the top of the process and then overwriting it in branches. State machines are often written with an enumeration type for the states, one process for the state register, and one or two processes for the next-state and output logic. Each choice has supporters, and the language accepts all of them.
- Access command fields (a).
  Scope: Accesses on a record port (never on non-record ports, even ones together carrying an access) addressing this unit's own registers, FIFOs, locks or memory words (not a cache's copies).
  Criteria (any of): (1) the fields only saying whether an access happens, its direction and which register, FIFO or bytes it reaches (a strobe, a read or write bit, register-select address bits, byte enables; an address indexing a memory's stored words is the access address, not one of them); (2) a write enable whose assignment reads only these fields and that only lets a register or FIFO take the written data.
  Exceptions: Not covered: a request held until served, a select routing it on, and a strobe driven on to a unit output port other than as an acknowledge; an operation's start pulse (not an access's strobe or write enable).
  Outcome: they are part of the information the access writes or reads, not information of their own; such a field whose value a register takes as its new content belongs to that register's piece. They are not pieces of their own, although steps 1 and 2, Build-time values and Per-region checks would keep some: keep no concept for them.
  Evidence: cite no line only testing them, or only assigning such a write enable, as a held line.
- Access command fields (b).
  Scope: A signal of its own decoded from these fields.
  Criteria (any of): (1) gates or masks what a read returns (a read enable, a select also masking read data); (2) pops a FIFO of data the unit generates itself.
  Exceptions: An inline condition is no such signal, nor is a strobe of a FIFO that Port buffers covers.
  Outcome: it is its own piece (step 2): name it by what it decides; no step-3 clause folds it.
  Evidence: hold it at the line assigning it.
