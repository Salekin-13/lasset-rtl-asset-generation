THIS CALL: PHASE 1, CONCEPTUAL ASSETS

For each UNIT of the diagram:

1. Interface. Name information entering or leaving through the unit's INPUTS and OUTPUTS: data received, held or returned; settings and configuration; state and status; commands, requests and responses; events signaled to other modules.

2. Inside. Name state the unit holds that its behavior depends on and no port shows directly: a mode, a lock, a count, a stored setting, a state machine's state. Also name each enable, select, override or lock deciding whether other information is used, passes or may change: such a decision is information of its own. Neither sentence covers sequencing state outside a coprocessor (a rule below).

3. Merge and split. Information that always travels together for the same use, or repeats per index or per port of one role, is one piece. Information with different uses is separate, even on a shared port. An internal signal only timing one step of other information (an increment pulse, a started flag, a one-cycle request) is part of what it times, not its own decision. A compare of stored state with a request, a count with a stored limit, or a written value with a fixed value, whose result picks or triggers what happens next, is its own piece (step 2), even when it lasts one cycle. Hold it where computed; never merge it into its inputs or the action it triggers. Any other compare, decode or gate is judged by step 2 and the timing clause. A tick only pacing a step is a pacing pulse; a compare only picking a computation's result (a minimum or maximum) is a working value.

4. Rubric. Per piece, answer each question "yes" only when both parts hold: first, what the information is, judged from what the RTL does with it; second, a mechanism the RTL shows or the black-box rule (section 1) gives.
   Confidentiality. Assume the IC integrating the IP requires confidentiality protections. Is this information, received as input or generated inside the IP, something an integrator may consider secret? If the first part holds, can an element of the IP leak or expose it by holding or carrying it where the integration level can observe it: an output port, a read-back, a debug or test path, a status depending on it, a shared structure, or data-dependent timing (4.4)? Phase 2 judges authorization, so a designed use never makes the second part "no".
   Integrity. Assume the IC integrating the IP requires integrity protections. Is this information material an integrator may deem sensitive, or a state or configuration setting that must be immutable during certain operations or modes? If the first part holds, can an element of the IP modify it?
   Availability. Does this information gate (enable, block or select) an output port or an input port's use, or would the IP or IC stop working without it? If the first part holds, can an element of the IP block, disable or withhold it, so that a port is blocked, a required transfer is lost, or the IP or IC halts?
   Undermined expected behavior. Does a privileged mode, an override, a bypass, test-packet injection or similar integration-level behavior act on this information? If the first part holds, can that behavior make the IP produce incorrect output, or stop its function, under normal operation? Focus on what may be compromised.

5. Keep. Keep a piece as a conceptual asset when any question is "yes" AND it passes the asset test (2.3); list the rest under "Not Kept". Phase 2 sees only kept concepts, starting from their held lines.

6. Anchor. Under "Enters Through" list each unit port whose value is carried (2.2) into the information; under "Leaves Through", each unit port written by an element carrying it; either may be empty. Skip ports that only decide the information or that it only decides. When a state machine, apart from reset, changes state only at steps a peer device's clock paces, and its next state depends only on its current state and one bit of a non-record input port (directly or through synchronizer stages), that port, never the peer's clock line, is the input port setting the state (2.6), though only conditions test its bit (an implicit flow, 2.2). List that port under "Enters Through" of the concept holding that state; the skip above does not apply to it. Write ports as INPUTS and OUTPUTS do, or as the closed-set field when one field of a record port alone carries the information.

Rules (read before answering):
- Describe a conceptual asset by what the information is, not an element name. A diagram arrow shows a flow, not an asset.
- Precedence. A rule's bar is its sentence saying information is not a conceptual asset or not a piece of its own. What a rule judges as usual or does not cover is spared only from that rule's bar.
- Reading a rule. Check its scope, then each criterion, then each exception it lists, in that order, against the RTL; where a criterion says "only", "every" or "one element", check every assignment or use, not one. Its outcome follows only for an element in scope that meets every criterion (one, where marked "any of") and that no listed exception covers.
- Debug module registers.
  Scope: a debug module or a debug transport unit (a unit whose ports are a debug bus, a test-access port or both, and whose registers are debug control, status, command, program-buffer or data-exchange registers). In it, a signal or record field, never a port: such a register or a field of one (an activation, halt, resume or reset control bit; a hart-halted, hart-reset or resume-acknowledge status; a command word, a command-error code, an automatic-execution setting, a program-buffer word; an authentication exchange word or state other than the valid flag), and the state of the machine serving those accesses.
  Criteria: (1) the debug bus, the test-access port or the hart's debug-mode accesses write it, and it is read to sequence, gate or report debug operations; (2) it is not one of the spared elements below.
  Exceptions:judged as usual (2.4, 4.4): the register selecting the hart, the register exchanging data with the hart, the authentication valid flag, a busy flag of the transport or module, and the unit's own ports (its halt and reset requests, its debug-bus and hart-side inputs and outputs).
  Outcome: it only holds or decides what the debug ports deliver: not a piece of its own, although step 2, step 3, Held outcomes, 2.4, 4.2 and 4.4 would keep it: keep no concept for it, name it in no concept's information, and cite no line assigning it as a held line. What the halt-request and reset-request outputs deliver stays a piece of its own, held at the port (2.6: the output port returning it) even where the only register driving the port is barred: keep that concept, list the port under Leaves Through, cite the port's assignment line as its held line, and put the barred register under Not Kept, never the port. The other spared elements and the unit's inputs are judged as usual: keep their concepts and their labels (user decision 2026-10-19: reference convention).
- Clocks and resets. Clock and reset inputs, a reset request the unit only combines, gates, registers or passes to a reset chain or reset output port (its copies and that output port included), and chains only synchronizing or releasing a reset (a reset shift register, a registered reset copy) are not conceptual assets under any question. A serial link's clock line the unit drives to, or senses from, a peer device is not a conceptual asset either, nor is a setting or decision whose only use, apart from a read-back, is to shape that line (polarity, phase against the data, holding it while the peer stretches it), although this rule judges other clock settings as usual. Do not cite their lines as held lines. The link's data and select lines, its rate setting and the unit's clock-enable outputs are judged as usual. A setting's only use is to shape a serial link's clock line also when, apart from its read-back, its counterparts show it gives value to or decides only the element driving that line, and that element gives value to or decides nothing but the line, even where the line's phase sets when the peer samples or sends data. It is then not a piece of its own: keep no concept for it and do not cite its lines as held lines; a transfer-mode, format or rate concept holding other settings stays, without it. Clock-controlling settings or requests (an enable, a rate) are judged as usual, as is a reset-triggering decision (a timeout) where it is computed, not a copy the unit only gates or registers, except as the next sentence says. A decision that a write was refused or carried a wrong value (a write while locked, a wrong password), its gated or registered copies, and a setting choosing only whether such a violation resets are not conceptual assets either when, apart from a read-back, they only request a reset and record its cause, although step 3 makes a compare of a written value with a fixed value a piece. The cause record, the lock refusing the write, and a compare outcome restarting a counter are judged as usual.
- Build-time values. A generic or constant only fixing the build (a feature switch, size or depth, fixed address or address map, buffering choice) is not a conceptual asset: no element of the IP can change or withhold it at run time. Nor is a run-time bit that a statement ANDs with a build-time switch and whose effect includes writing characters to a file or the screen (a simulation-only mode), although a bus write can change it: it is part of that build choice and is not the run-time decision the next sentence asks for. Instead, name the run-time decision using it as its own concept (which port an address selects, which requester is granted).
- Pacing pulses.
  Scope: A tick, edge pulse or divider count made inside the unit, including a done, write or pop strobe set inside a test of a tick or edge pulse this unit makes, or a wire copying such a strobe, or the strobe at the end of a register chain (registers in series, not one register; not the chain's earlier stages); or an input port or a field of one, used only as a condition (2.2: at the end of that path it is only tested, never combined into a value by a logic or arithmetic operator) (directly or via wires or one register picking its bits, not a register chain) letting a tick or count advance.
  Criteria: (1) only to pace another step.
  Exceptions: any output port of any entity in this file, whatever drives it, and a pulse (never a count, a count's copy, or a bit of one) that such a port gets value from directly (2.2); an enable deciding whether the count runs at all (not a tick letting it advance one step); a request held until served; a start pulse or an access's read, write or pop strobe, or its wire or one-register copy (not a register chain), decoded from a received command or access; a count whose compare with a limit raises a reset, error or interrupt, or sets an output level, and that compare's flag; a bit, word or step counter that restarts with each transfer or operation, not only when disabled or at its own limit (sequencing state, below, judges it). This rule does not cover a non-record input port, not a record's field, that a state machine's next-state condition tests directly, not through a synchronizer (a done or wait flag); a pulse that is a term of a count's sum (2.2: explicit flow; a pulse only tested before an increment is a condition, still covered); or the input port whose value is that added pulse: it carries into the count, so step 3's timing clause does not fold it. The carry bit out of a count's own sum stays covered.
  Outcome: part of that step or its rate setting (step 3). Do not name it in any concept's information or cite its lines as held lines.
- Forwarded transactions. A bus transaction (a request or response with its address, data and handshake) that the unit only forwards between its ports or to a sub-unit, without storing, computing or deciding it, is not a conceptual asset of this unit; this rule, its sentences on relayed data included, never covers a bus whose address this unit drives on a non-record output port of its own and whose acknowledge it takes on a non-record input port of its own (judge from port names which ports are that bus's address, acknowledge and other lines, and say so): the request it drives onto that bus's ports and the response it takes from them are judged as usual, as information leaving and entering the unit there. Also forwarding: merging several ports' bus responses into one (an OR or a multiplexer); a register stage passing a whole request or response record on unchanged a cycle later, although it stores the record; and a record this unit only wires between one of its ports and the port map of an instance of another IP, with no statement of this unit reading or writing it (a constant tied to it in a generate branch lacking the instance is no such statement), even though the black-box rule lets the instance change it. The decision whether or where it passes is judged as usual. Relayed data is data a transfer carries into or out of the unit (data loaded or stored, instruction words fetched, messages received or sent) when no statement of this unit stores it or computes from it: it only moves between a unit port and an instance of another IP, between such instances, or into a statement only mixing it with other values (an OR, a multiplexer). Relayed data, alone or with only the acknowledge and ready lines timing its transfer, is not a piece of its own, even in a unit executing instructions and although step 1 names data received or returned and 4.2 end-user's private data: keep no concept for it. Judged as usual by this rule only: a transfer's address and direction; a wait or fault flag; an interrupt or debug request; a register read-back word, and the register contents an instance holds; an arithmetic, logic or compare result an instance computes from operands; the value a mixing statement writes (such as the value written back to a register); and data the unit stores, shifts through its own register, generates or computes from, even when a buffer instance also holds it. Judge from port names which instance ports carry relayed data and which a computed result, and say so.
- Forwarded-access stages.
  Scope: in a test or debug access port (serial data ports a peer's clock paces; bus request record output, response record input (2.6)), a register (not a port) staging the forwarded access or its data shift register.
  Criteria (any of): (1) a stage: its only non-constant source is one slice of that shift register or the response's data field; it gives value only to request fields or a capture wire; no condition reads it. (2) the shift register: at one step it loads a capture wire's word, else shifts in the serial input's bit, directly or through synchronizer stages; it gives value only to itself, the serial output and registers (1) covers; only that loading condition's inline compare reads its bits.
  Exceptions: judged as usual: a shift register setting tested registers (its settings), and those registers; computed flags (busy, error); the serial ports; an address or operation code this unit decodes or indexes with, or tests other than in the inline compare criterion (2) names.
  Outcome: (2.6: copies kept while moving): its address, data, operation code and returned data are not this unit's information, although step 1 names requests and responses, 2.6 the element an access sets or returns, Forwarded transactions a transfer's address and direction, and Serial shift registers only a self-paced link. Keep no concept for them, name them in no concept's information, cite none of their lines as held lines. Flags, settings and serial ports: judged as usual, the ports under the settings' concepts.
- Second copies. An internal register (not a port) that directly copies bits of one other register of its own entity, not as an index, whose other assignments write only constants, and that no condition reads, is a copy kept only while the value moves (2.6). It is not a piece of its own: name its information under the copied register's piece, and do not cite its lines as held lines.
- Bus handshake copies. A bus response acknowledge only repeating or delaying the bus request strobe, and a bus error flag tied to a constant, are not information of their own. In a unit passing bus requests from an input bus request port to an output one, a register of one bit, or one bit per requester, not a request waiting for a grant (a rule below), holds no information of its own when every assignment to it (directly or through its next-value signal), apart from clearing or holding it, copies or ORs in only the strobe, lock bit or response error bit of the access in progress, or sets it when a test reading only that access's fields and build-time values holds (a route bit), and the unit reads it only to start, pass on, route, time or end that access, the access it serves or that locked sequence, or to drop words that access fetched: the register only re-times a value the access already carries. It is not a piece of its own, although steps 1 to 4, Build-time values and 4.4 would name it a request, status, lock, select, compare or bypass, and even where another rule judges a decision or held request as usual. A compare or decode reading a register this rule bars, and otherwise only that access's own fields and build-time values, or used only to set such a register, is part of that register (step 3), not a piece of its own. Keep no concept for them and cite none of their lines as held lines, except a line also assigning an element this rule does not bar. Judged as usual: the grant, its select and strobe; an address decode choosing which of several output bus request ports gets the access; a pending fence or flush clearing what the unit stores; a busy flag set when the unit itself issues an access; a timeout count, its error and its suppression flag; a reservation; a software-set lock guarding later accesses; a read enable deciding whether stored data leaves on the response; and a cache's hit. A one-bit register that one unconditional statement sets on every clock edge to a stored state bit or flag of this unit, copied or inverted and ANDed only with terms saying when it applies (a request strobe, its read or write bit, an operation-type decode), and that only a bus response's acknowledge or data fields read, only re-times that state to the response. It is part of that state, not a piece of its own, although step 1 names status and responses and step 3 makes a compare of stored state with a request a piece: keep no concept for it and do not cite its lines as held lines. Judged as usual: that state, where held; a register set only from the unit's input ports (a read enable from a strobe and a read or write bit); and a flag that a condition sets to a constant (a timeout error raised at a count's limit).
- Response merges and re-timings.
  Scope: in a unit with input bus request and output bus response record ports, an internal signal or field (not a port's) whose readers (it has some) are only response output fields (directly, in an OR or AND, or via a register stage), a multi-operand result, or its own next-value copy.
  Criteria: (1) apart from constants and itself, built only by copying, inverting, OR-ing or AND-ing response record fields (a port's, or an array's copying them), non-record input ports, this unit's one-bit (not vector) state, flag or decode bits, and the request's strobe or read-write bit; never arithmetic, shift, compare or memory results, nor the request's address or data; (2) no condition, selector or index reads it; (3) assigned every cycle, or every cycle of one state (even one the strobe entered).
  Exceptions: not covered: a flag a condition sets only to constants; a register set only from a non-record input port (an input sample or synchronizer stage; Bus handshake copies).
  Outcome: a carrier (2.6), not a piece of its own, although step 1 names status and responses, step 2 each decision, and Forwarded transactions and Bus handshake copies spare a wait or fault flag this unit raises and an input-sample register (never merged response errors, a re-timed fail bit, or a register also taking a response field, state bit or flag): keep no concept for it, name it in no concept's information, cite no line assigning it as a held line.
- Working values. Partial results inside a computation (a partial sum, product or round value, a synchronizer stage, a debiasing step) are part of the result they produce (step 3), not concepts of their own. So are the state and flag made inside a debiasing step to choose which raw bits it accepts: although step 2 would call them a decision, they only shape that result, like a compare picking a minimum (step 3). Do not name a synchronizer stage in any concept's information or cite its lines as held lines.
- Slices. A signal (not a port) whose only assignment copies part of one element's bits (a slice), or joins signals each doing so from the same element, only carries that element's value (2.2), unless that element is a bus request or response record port or a field of one: such a slice is judged as usual (2.6). Otherwise it is not a piece of its own: do not cite its lines as held lines.
- Hand-offs. Check each port-map line where an instance's non-record output port drives a signal another instance or this unit's logic reads. A wait, fault or write-enable flag, or an access address, that one instance outputs on a non-record port to another instance or this unit's logic is a hand-off; if the RTL cannot show which it is, judge from the port names at either end and say so; a field of a record an instance outputs is never a hand-off, even wired alone into another instance's non-record port. A hand-off is its own piece (step 2), unless Port buffers covers it (then this rule does not apply). No step-3 clause or other rule folds it, even when it travels with the data it qualifies, when another instance outputs the same address earlier or later (cite each output's port-map line, in one piece), or when it is one bit of a count: then hold it at the line assigning that bit to the instance output, and a count kept only to make it belongs to this piece.
- Decided-on instance outputs. A value that an instance of this file outputs on a non-record port, other than a hand-off, crosses into this unit whole at the unit signal that port drives through the port map when that signal's closed-set entry gets its value from that instance port and lists "decides" partners, because this unit's decisions then use the value only through that signal (2.6, outward: the instance output this unit then uses as the value itself); when that signal lists no "decides" partner, this sentence does not apply. Hold such a value also at the port-map line wiring that port to that signal (unless the Port buffers rule bars citing that signal's lines), besides any line where the instance computes it; this rule sets only where the piece is held, not whether it is kept.
- Held outcomes, addresses and settings. Where an accepted compare outcome, an access address or an operand setting is held: the outcome of a compare of a written value with a fixed value is held at the register that the branch taken when the value matches sets, as that register is where the compare is computed (step 3) even when it keeps the outcome for one cycle only and only restarts a counter, so it is neither the action the compare triggers nor a one-cycle request folded into what it times, and the line where the other branch requests a reset is never its held line; an access address that leaves the unit in the address field of a bus request record port, which never holds it (2.6), is also held at each non-record port on which an instance of another IP outputs that address to another instance, judged from the port names at either end (an address output, or an output wired into an address input) as a hand-off; and a setting decoded from instruction fields that changes how operands are read (signedness), not a flag only naming the operation, is held at the lines assigning it, even inside a concept about the operation it belongs to; Phase 1 cites each such line as a held line of the concept whose information it is, and Phase 2, at the block owning each such line, names the element the line assigns, even when no arrow it follows lists that element, and labels it primary for that concept.
- Instance-driven records. A record driven whole by one instance of another IP and wired whole into one or more other instances' port maps (decoded controls or fetch results between sub-units; closed set: the record's own entry gets its value from one instance port and gives it only to instance ports) holds nothing of this unit, even if a port map also takes a field alone, a statement of this unit reads one, or it carries the instructions this unit executes: that instance holds each value; the record and its fields, one-bit flags included, only carry copies, and none is a non-record signal. So information such a record or its fields carry, and that no other element except bus request or response record ports stores, computes or passes whole across the boundary (2.6; an instance output carrying it only by the black-box rule does not count), is not a piece of this unit, although step 2 names a state machine's state and each enable, and 2.4 and 4.2 the privilege mode and program counter: keep no concept for it. Information a non-record unit input port itself brings in crosses the boundary whole at that port (2.6), even when the port is wired straight into that instance: list the port under "Enters Through" and hold the information at the line wiring the port. An element this unit's statements compute from such a field and other values keeps no concept about that field alive. Cite no declaration or port-map line of such a record or its fields as a held line. Judged as usual: non-record signals handed between instances; non-record unit ports, even one wired straight into an instance (a debug or interrupt request line); records this unit's statements set, whole or per field; records whose fields port maps or several instances set separately; and, for its other values, an element this unit's statements compute from such a field and other values.
- Register read-back. In a unit executing instructions, the word an instance outputs for reads of its control and status registers, when a statement of this unit merges it directly into the value written back to a register, is its own piece: those registers' contents as software reads them. Hold it at that instance output; no step-3 clause or other rule folds it. In a unit executing instructions, a word that an instance outputs for reads of its own control and status registers, and that this unit reads only in an OR into the word another instance takes in to answer such reads, only carries those registers to the other instance's read-back: the registers (a count, a protection setting, a configuration or status bit) stay inside the first instance, and no statement of this unit stores, computes or decides them (a constant tied to the word in a generate branch lacking that instance is no such statement). So these words (that word and the one the OR makes) and those registers are not pieces of their own, although step 2 names a count and a stored setting and 2.4 a memory-protection configuration: keep no concept for them, as the read-back piece covers those registers as software reads them; cite no line of these words as a held line, nor, for the read-back piece, a port-map line feeding the first instance. Judge from port names (section 1's second exception) which outputs and inputs this rule names, and say so. Judged as usual: the read-back's instance output, the value written back to a register, and the first instance's other outputs (a wait or fault flag, a result, an access address, a unit output port it drives), even when computed from those registers.
- Port buffers (a).
  Scope: a FIFO instance's push and pop strobes, its fill flags (holds data, has room, half full), the line wired to its clear input, a command read only by such clear lines, and a push-while-full flag (even a register of this unit); never a FIFO holding data the unit generates rather than receives (random bits). Never in scope: a non-record unit port, even one wired straight to a strobe (a record port's field that is itself the strobe stays in scope); a push strobe decoded from non-record write-strobe and address ports; and the fill flags and clear line of a FIFO whose push strobe is so decoded.
  Criteria: the FIFO's write data is a unit input port's value (for example a bus write or response, or bits shifted in from a serial input port); for all but its push and pop strobes, also: a push or pop strobe of it is decoded from a field of an input bus request record port (2.6).
  Exceptions: judged as usual: the buffered data, an output port these flags decide (an interrupt request, a ready-to-receive line), and a unit enable also clearing the FIFO.
  Outcome: not pieces of their own, although step 2 would call some a decision: the FIFO only buffers data between two ports; they only time, gate, clear or report on that data.
  Evidence: cite no line assigning or wiring them as a held line; judge from port names that an instance is a FIFO, which outputs are its flags and which ports carry its data, and say so.
- Port buffers (b).
  Scope: only a FIFO whose write data the unit generates rather than receives at a port (random bits).
  Criteria (any of): (1) its holds-data flag that a statement of this unit tests to return either that data or something else (the flag withholds the data); (2) a register whose only use is to clear that FIFO (it discards the data).
  Exceptions: Port buffers does not cover its other flags or its push, pop and enable controls.
  Outcome: each their own piece (step 2) that no step-3 clause folds into that data. If the flag, then held at the line wiring it out of the FIFO, with the read-data line returning the flag as its exit (step 6). If the register, then held at the line assigning it.
- Port buffers (c).
  Scope: any FIFO instance, whatever data it holds; signals (not ports).
  Criteria (any of): (1) wired to its write-data input; (2) driven by its read-data output.
  Outcome: the FIFO keeps each word only while the word moves (2.6: a copy kept only while the value moves); they only carry the word and are not pieces of their own; the buffered data is judged where the unit generates it (random bits) or where it crosses the unit's boundary at a port.
  Evidence: cite no line assigning or wiring those two signals as a held line; leave "Held Lines" empty if no other line holds the data.
- Sequencing state.
  Scope: units other than a coprocessor, a unit shifting in random bits it generates, or a test or debug access port with a clock input port a peer drives, besides the unit's own clock (say which, from its ports and entity); in them, a state machine's state register (a test of its own value picks its next value) or a bit counter, phase counter (even a divider count reloaded at each bit of a transfer), word counter or step counter; the next-value wire such a register copies at each clock edge shares its decision.
  Criteria: (1) restarts with each transfer or operation the unit performs, not only when disabled or at its own limit (even if one bit copies an enable or a queued command picks the first step); (2) is read only to pick that transfer's next step, to time or gate any other element (strobes, shifts, loads, multiplexers, flags, counts), or to point its address at the next word.
  Exceptions: this rule does not cover, so judge as usual: anything in a coprocessor, whether or not the last sub-rule keeps it; a port, even one its bits or flags give value to or decide, or whose bit picks its next step; an enable or rate setting; another element its steps load or drive (a chip-select register, an address); a flag a request or command sets, held until that request or its locked sequence ends, however it ends; a reservation one access sets and a later one checks; the current grant (a state naming which requester holds a shared path) and the select and strobe it drives; a count, other than a transfer's bit counter, whose compare with a limit raises a reset, error or interrupt, or sets an output level (a timeout or timer count), that compare's flag, and a timeout's suppression flag.
  Outcome: sequencing state: it only orders steps of information other elements hold, so it and its busy and done flags (below) are not information or pieces of their own, although step 2 names a state machine's state, a count and a select, and 2.4 control flow (a program's): keep no concept for them.
  Evidence: cite none of their lines as held lines, except one also assigning an element this rule does not bar.
  - Scope: in the same units, a flag, not a port.
    Criteria (any of): (1) a busy flag decoded from sequencing state alone (every element it gets value from or is decided by); (2) a done flag only sequencing state sets, at its last step (every line raising it, none a port map).
    Exceptions: a flag a test reads to block a request port's write into a register of this unit while it is set: a lock (step 2: information of its own), so judged as usual.
    Outcome: part of sequencing state (above).
  - Scope: a one-bit non-record unit input port.
    Criteria: (1) its bit is read, directly or only through synchronizer stages (registers only shifting that port's bit along, and wires only copying one of their bits) that give value to nothing but each other, only in conditions picking a state machine's next state, even if those conditions also set other elements (list each stage's counterparts); (2) no conceptual asset holds that state; (3) not a clock, a reset or a serial link's clock line.
    Outcome: the port's bit is that peer's command or status to the state machine, information of its own whose primary is that port (2.6: the input port setting it), never that state register, which the bit only decides (2.2), nor those stages.
  - Scope: in a coprocessor, a count.
    Criteria: (1) a multi-cycle operation steps it every clock cycle of its busy state; (2) its end test only leaves that state.
    Outcome: a step counter: information of its own, one piece with that state. Keep that state as a concept and hold the count in it, not in the operation's result or its pacing.
- Serial shift registers. In a unit shifting data bit by bit onto or off a serial data port, paced by the unit's own rate setting, the data shift register only holds each word while moving it between that port and the element taking or giving the whole word, so the port is where that data crosses the unit's boundary whole (2.6). Keep the data as a piece: list that port under "Enters Through" or "Leaves Through" and cite the lines reading or driving it as entry or exit lines, even when they name the shift register; cite no line assigning the shift register as a held line, and leave "Held Lines" empty if no other line holds the data.
- Buffer and engine status bits. A status bit a bus read returns is not information of its own when every element it copies (even inverted) or combines is barred by this call's rule on a FIFO only buffering data between two ports (never a flag of a FIFO holding data the unit generates itself) or on sequencing state: it only tells software whether the buffered or shifted data can move or was lost, which that data, its settings and the output ports these elements decide already cover. Although step 1 names status and 4.3 status signals, keep no concept for such bits, alone or grouped as the status software reads, and cite no read-data line returning them as a held line. Not covered: a bit returning anything else, even in the same read word (a stored setting, selection or lock, a reset's cause record); it belongs to the piece it returns, as that piece's exit (step 6). Not covered either: the output ports these elements decide (an interrupt request, a ready-to-receive line), a register a test or debug access port shifts out, and, in a unit executing instructions, the word an instance outputs for reads of its control and status registers.
- Port options. A setting a bus write stores is a port option when, apart from its read-back, its counterparts show it gives value to or decides some element, and each is an interrupt request output (it picks which events raise it), a flow-control handshake output, or an element decided at a test letting a flow-control handshake input (or its synchronized copy) hold a transfer: it only tunes those ports, which carry the outcome. Judge from port names which ports are interrupt requests or flow-control handshakes, never a serial link's clock line, and say so. Judged as usual: those ports, and a setting with another such element (an enable also copied into engine state, clearing a buffer or driving a clock-enable output; a rate setting; a lock; a limit compared with a count). A port option is not a piece of its own, although step 2 names each enable, step 3 splits by use and it gates an output port: keep no concept for it, name it in no concept's information, and cite no line assigning it as a held line. A concept also holding a port it tunes stays, for that port alone.
- Cached copies. In a cache (a unit answering a read from its own copy when a stored tag matches the address, else fetching the words over a backing bus), the copied words copy backing-memory data, and the tag and valid bits only record which words are copied: none is a piece of this unit, although steps 1 and 2 would name them and 4.4 names caches. Judged as usual: its decisions (the hit, the bytes a write changes, the address, its fill, clear and invalidate commands, a pending fence or flush), and a memory that is itself the store.
- Stored-word arrays.
  Scope: an internal array (never a port) in this file holding a memory the unit itself stores or a cache's copies, written on a clock edge at a word a run-time index picks (never a constant or generate-loop index).
  Criteria: (1) it is written only with a bus request or response record port's data field, whole or sliced, directly or through chained signals, record fields or child-entity input ports that only copy or select among such fields; (2) its only use copies a picked word into one read element, a unit signal holding the read word (closed-set type reg or other) or a child entity's read-data output port, never a unit non-record output port, condition or operand.
  Exceptions: judged as usual: a register file or key store; the read element, address, read enable and write enables; tag and valid arrays.
  Outcome: not a piece of its own, although step 2 (stored state) and 2.6's storage and bus-port clauses would hold the stored words at it: keep no concept for it, name it in no concept's information, and cite no line writing it as the stored words' held line. Where the unit is the store, those words are one piece held at the read element (not relayed data). In a cache, keep no concept for them (Cached copies): a cache is not the store of what it copies, although that rule's store exception and Forwarded transactions' "data the unit stores" could seem to name its data array.
- Held addresses. A register whose value, apart from constants and itself, comes only from part of an access's address field, directly or through its next-value wire (a wire giving value to or deciding nothing but that register) or a wire only copying that part, and that only feeds other addresses or indexes a memory, holds that address only while the access is served (2.6: a copy kept only while the value moves). It and its next-value wire (not a wire only copying that part and also giving value to or deciding another element: that wire is the address's own element, judged as usual) are part of the access address, not pieces of their own: do not cite their lines as held lines.
- Memory access address. In a unit that is itself the store of a memory (an array it assigns on a clock edge, not a cache's copies), a wire whose only assignment copies or slices the address field of a bus request record port (closed set: role "index", and that field is its only "gets value from" partner) and whose value picks which word of that array an access writes or reads is a select (step 2) deciding which stored word the access uses or changes, so it is a piece of its own, the access address, even though the unit returns it on no output port and holds it in no register, and although Access command fields lists register-select address bits and byte enables, step 3 would merge it into the stored words or the access, and 2.2 calls its use an index flow (that flow carries the address into the word read; it does not make the address only a path to the stored words): a changed address makes the access write or return a word it was not aimed at, so judge its rubric by that mechanism, and hold it at the line assigning it (not its registered copy, which Held addresses bars).
- Operation selectors (a).
  Scope: In a unit executing an instruction or atomic memory operation a processor issues to it (a processor or its execution unit, a coprocessor, a cache).
  Criteria (any of): (1) instruction or request fields only picking the operation or its result form (an opcode, a function code, an instruction-type bit, even one also starting the operation); (2) their stored copies; (3) flags decoded from them only naming the operation. A flag whose assignment reads more than these fields (a start or valid signal, a state) does not only name the operation.
  Exceptions: (1) Judged as usual: a start command or pulse that is not a field of an input record port, saying when the operation starts, even one decoded per operation (a multiply or divide start) or held until served (ORed into a register); a register access's address and write enable; a completion flag or one-bit non-record output port, even one copying a criterion (3) flag; and a setting decoded from them (not a copy) changing how operands are read (signedness). (2) Not covered: a plain bus read or write, its read or write bit and a read enable made from it; a code this unit decodes (2.6) from these fields and only copies into a bus request output field, but this rule covers that output field.
  Outcome: they are part of that operation (step 3), not pieces of their own, although step 2 names a select.
  Evidence: Do not list them under "Enters Through" or cite their lines as held lines, except a line assigning an element this rule judges as usual.
- Operation selectors (b).
  Scope: In the same units, a register.
  Criteria: (1) whose value, apart from constants and itself, comes only from one source operand input (a port or a request-record field, not of a bus request (2.6)) when the operation starts, directly or through its next-value wire; (2) reaches an output port only through the element holding the result.
  Outcome: it only holds that operand while the operation uses it (2.6: a copy kept only while the value moves). It and its next-value wire are part of that operand's piece: keep that piece, list the operand input under "Enters Through".
  Evidence: cite the lines where it takes the operand as entry lines; do not cite them as held lines.
- Access command fields (a).
  Scope: Accesses ending in this unit's own registers, FIFOs, locks or memory words, in an instance's that this unit's statements decode or gate the access to, or in a FIFO instance a field pops straight, never in a cache's copies. They come on an input record port of this unit, a processor's control record port included (never on non-record ports, even ones together carrying an access), with the write enables built from their fields; this rule does not cover the record port itself. Never a request leaving through an output port, even one this unit builds, nor a record one instance drives into other instances' port maps, nor any field of it.
  Criteria (any of): (1) the fields only saying whether an access happens or is forced, its direction and which register, FIFO or bytes it reaches (a strobe, a read or write bit, register-select address bits (a control record's register numbers are such bits, even ones indexing a memory), byte enables; any other address indexing a memory's stored words, even one this unit chooses among register numbers, is the access address, not one of them); (2) a write enable whose assignment reads only these fields and signals decoded from them (even a select this rule does not cover) and whose only use lets a register or FIFO take the written data, in this unit or at an instance's write-enable input (judged by its port name; say so).
  Exceptions: Not covered: a signal (b) keeps; a request held until served, a select routing accesses on, even one with a bit per same-kind entry decoded from the register-select bits alone (that select only, not these fields; 2.6), and a strobe driven on to a unit output port other than as an acknowledge; a write enable also ANDing in the negated result of comparing the register-select bits with a fixed value (a write-permission decision refusing writes to that entry, step 2, one piece with that compare; not these fields); an operation's start pulse (not an access's strobe or write enable).
  Outcome: they are part of the information the access writes or reads, not information of their own; such a field whose value a register takes as its new content belongs to that register's piece. They are not pieces of their own, although steps 1 and 2, Build-time values and Per-region checks would keep some: keep no concept for them.
  Evidence: never list them under "Enters Through"; cite no line only testing them, or only assigning such a write enable, as a held line.
- Access command fields (b).
  Scope: A signal of its own decoded from these fields.
  Criteria (any of): (1) gates or masks what a read returns (a read enable, a select also masking read data); (2) pops a FIFO of data the unit generates itself.
  Exceptions: An inline condition is no such signal, nor is a strobe of a FIFO of data received at a unit input port.
  Outcome: it is its own piece (step 2): name it by what it decides; no step-3 clause folds it.
  Evidence: hold it at the line assigning it, never at a line (a) bars; list no field it is decoded from under "Enters Through".
- Per-region checks. When the unit makes the same compare or permission check per region or entry and only combines the results (a priority chain, an OR) into one decision, that decision is the piece, held where they combine; the per-region results are its working values (step 3), although step 3 makes a compare of stored state with a request a piece. A per-entry result itself picking where a request goes or which entry an access changes (which port an address selects, which lock is addressed) stays its own piece.
- Arbitration bookkeeping. A register only remembering the previous grant for round-robin priority (not the current grant, its select and strobe, or a request held until served) holds no decision of its own: it only tilts the next grant. It is not a piece of its own, although step 2 names a select: keep no concept for it, nor cite its lines as held lines.
- Requests waiting for a grant. In a unit with a test choosing which of several requesters an output bus request port serves (it reads each requester's request strobe and assigns which one holds that port), a one-bit register per requester whose assignments, apart from reset and clearing it while that requester holds the port, only OR in that requester's request strobe, and that this test reads, stores a request taken and not yet served; the signal the grant's statements set that drives that port's strobe field decides whether an access passes on, not who holds the port: each is information of its own, apart from the grant, which the state register naming the holder and the select hold; this rule does not cover lock bits copied from the requests' lock fields or a register only remembering the previous grant. Step 3's timing clause and the rules on bus handshake copies, arbitration bookkeeping, sequencing state and pacing pulses do not cover such a register or that strobe signal: keep the waiting requests as one piece and the strobe signal as another, each apart from the grant, and cite every line assigning them as held lines, reset lines included.
- Processor context fields. A field, of a record input port other than a bus request or response record port (2.6), that tells the processor's privilege mode, whether it is in debug mode or takes a trap, or whether the current access is a fetch or data access, read or write, only refines a decision this unit computes from other information when this unit only tests it (a condition, select, compare with a fixed value, gate on another result), directly or through a wire only selecting between such fields: the processor holds that state; the record carries a copy. Such a field or wire is part of the decision it refines (step 3), not a piece of its own, although steps 1 and 2 would name it and 2.4, 4.2 and 4.4 point at privilege and debug modes: keep no concept for it, nor list it under "Enters Through" or cite its lines as held lines, except a line assigning an element this rule judges as usual. Judged as usual: the decision such a field refines, where computed or stored (a permission verdict, fault output, execution state); the access address, compared with stored state; and the address, write enable and data of a write to a register of this unit. Not covered: the whole record port, a non-record input port (a peer's flow-control line, an interrupt or debug request), and a port or field wired into an instance. Judge what a field tells from port field names and their uses; say so.
- Control record ports.
  Scope: a record port of the unit, input or output, other than a bus request or response record port (2.6) or a record one instance of another IP drives whole into other instances' port maps (Instance-driven records); and its fields.
  Criteria: (1) this unit's own statements read its fields (an input: in conditions, selectors, indexes or as operands) or assign them (an output); (2) the fields carry what the processor decided for this unit, or what this unit decided for the processor: enables, selects, register numbers, instruction fields, mode bits, and the data words that travel with them.
  Outcome: the record is one port and one boundary: whatever a kept concept takes from it or returns through it crosses the unit's boundary whole at that port (2.6: the input port setting it, the output port returning it), and a field is a slice of that port's value (Slices), not an entry or exit of its own. So list the whole port under "Enters Through" or "Leaves Through" of each concept that takes or returns information through any of its fields, although step 6 says to write the field when one field alone carries the information, and although other rules say not to list certain fields: the port, not the field, is the entry or exit. Each such concept keeps the whole port as its entry or exit element (it is that concept's "Enters Through" or "Leaves Through" port). This rule keeps or drops no concept of its own; the rules on the fields' information still judge that information.
  Evidence: cite the lines reading or assigning the fields as entry or exit lines, as usual; write the port as INPUTS and OUTPUTS do, never a field.
- Access command ports.
  Scope: a non-record input port of the unit itself (not a field of a record port; not a port of an entity this unit instantiates; not a clock, a reset or a serial link's clock line) on which an access into this unit's own registers, FIFOs or memory words arrives beside the data: the access's write strobe or write enable, its read strobe or read enable, or its register-select address.
  Criteria: (1) this unit only tests it, directly or in a compare with a fixed value (2.2: implicit flow), or uses it as an index picking a register, to let a register, FIFO or memory word take the written data, to return a stored word or to acknowledge or pop the read (a read strobe, even one that only drives an acknowledge), or to pick which register the access reaches; (2) the data the access writes or reads travels on another port.
  Exceptions: not covered: a data port; a start command of an operation (Operation selectors judges it); a tick or edge pulse letting a count advance (Pacing pulses); a port whose bit a state machine's next-state condition tests (a done or wait flag).
  Outcome: it brings the access command into the unit: whether an access happens, its direction, and which register it reaches. That command is a piece of its own (step 2: a decision whether other information may change or is returned), separate from the registers it reaches, although step 3 would fold a one-cycle strobe into what it times, and although Access command fields bars such fields of a record port (that rule never covers a non-record port; this one covers nothing else): keep one concept for it per unit, list each such port under "Enters Through", and hold it at the lines testing or indexing with these ports.
  Evidence: cite the lines testing or indexing with these ports as held lines; a port declaration is no held line.
- Entry selects and register addresses.
  Scope: in a unit holding several same-kind entries (the elements of one array, or the registers, counters, locks or channels a generate statement repeats), a signal (not a port) made from the register-select address bits of an access on an input record port: a select with one bit per entry, or an address choosing among register numbers (a multiplexer of such fields, even one forcing a fixed entry).
  Criteria: (1) apart from constants, its value comes only from those address bits, directly or through a compare of them with each entry's index (closed set: "set to constants only" with that address field as its only "decided by" partner, or "gets value from" only such fields); (2) it picks which entry the access writes, reads or updates: it indexes the array, or each of its bits gives value to or decides only that entry's write, read or update enables.
  Exceptions: not covered: a signal with one bit for a whole group of entries that says only whether the access is for that group at all (part of the access command fields); an enable that also reads the strobe or the read or write bit (Access command fields judges it); a select of stored state or of written data.
  Outcome: it picks which entry the access reaches, as an access address picks a memory word: a changed value steers the access to an entry it was not aimed at. It is a piece of its own (step 2: a select deciding which information changes or is returned), although step 3 would merge it into the entries or the access, although Access command fields folds the bits it is made from, and although Per-region checks would call its bits per-region results: keep one concept for it, apart from the entries and the enables it feeds.
  Evidence: hold it at the line assigning it; list no field it is made from under "Enters Through".
- Coprocessor progress state.
  Scope: in a coprocessor (a unit that executes an operation a processor's execution unit starts on it and returns the result with a done or valid line), a register or register field this unit's own statements assign (not a port, not an instance output, not a wire, except the operand setting named last): the busy flag set when the operation starts and cleared when it ends or is aborted; the register holding the done flag that tells the last step is reached, or its registered copy that releases the result; the step counter the operation loads at its start and counts while busy; and, the one wire covered, an operand setting decoded from the instruction and an operand that every step uses (a sign fill, signedness).
  Criteria: (1) this unit assigns it in its own statements; (2) a condition reads it, directly or through a wire computed from it alone (a run or done wire), to advance, end or release the operation; or the result or valid output is assigned from it; or the steps use it to form the result.
  Exceptions: not covered: the operand registers and the result (Operation selectors (b) and Working values judge them); a flag that only names the operation (Operation selectors (a)).
  Outcome: the operation's progress state: whether it runs, how many steps remain, when its result is valid, and how the steps treat the operand. It is a piece of its own (step 2: state the unit holds that its behavior depends on; step 3: not an internal signal only timing one step, since it decides whether the result is released at all), apart from the operands and the result; Sequencing state does not reach a coprocessor, Pacing pulses' sentence on a register recording that a count has started does not cover it, and Working values' partial results do not include it: keep one concept for it per operation, hold it at the lines assigning these elements, and list the done or valid output port under "Leaves Through".
  Evidence: cite the lines assigning the busy flag, the done flag, the counter and the operand setting as held lines.
- Done and wait inputs.
  Scope: a one-bit non-record input port of the unit itself (not a record field, not a port of an entity this unit instantiates, not a clock, a reset or a serial link's clock line) that a condition of this unit tests to pick a state machine's next state, or to clear the one-bit flag that holds an access pending.
  Criteria: (1) the test lets the unit leave a state, or clear a pending flag, in which it waits for an operation another unit or device performs (the condition's other branch keeps the state or the flag, and the unit moves on only once the port shows the operation done, valid, ready, acknowledged, failed or no longer busy); (2) the port comes from the unit or device performing that operation (judge from the port names at either end, and say so).
  Exceptions: not covered: a command or enable that starts, clears or gates something (step 2 judges it as usual); a request held until served; a tick letting a count advance (Pacing pulses); a port whose bit synchronizer stages re-sample first (Sequencing state's port sub-rule judges it).
  Outcome: it brings the peer's status into this unit: whether the operation this unit waits for has ended. That status is a piece of its own (step 1: a response signalled by another module; step 2: a decision whether this unit advances), although step 3 would fold a one-cycle flag into what it times and although Pacing pulses names an input port letting a count advance: keep one concept for it, list the port under "Enters Through", and hold it at the lines testing it.
  Evidence: cite the lines testing the port as held lines; name the state machine and the operation waited for.
- Link handshake ports.
  Scope: a non-record port of the unit itself on a streaming or serial link to a peer device or module, other than the link's data lines, its clock line and any bus request or response record: an input port wired straight, or through one register, into a FIFO instance's push or pop strobe input; an output port driven from a FIFO's fill flag, or from a register telling the peer whether this unit can accept or has a word; and a flow-control or chip-select line, even one that reaches the unit's strobes only through synchronizer stages and its state machine (judge from the port names which lines are the link's handshake, and say so).
  Criteria: (1) the port's value decides, at this unit's boundary, whether a word moves across the link; (2) the word it qualifies travels on other ports of the same link.
  Exceptions: not covered: the unit's internal strobes, fill flags and clear lines of the FIFO (Port buffers judges them); the link's data ports, which are judged as usual, as information crossing the unit's boundary; the link's clock line (Clocks and resets).
  Outcome: the handshake is the link's transfer protocol at this unit's boundary: whether the peer offers or accepts a word, and whether this unit does. It is a piece of its own (step 1: a request or response signalled to or from another module; a line held still blocks every transfer), although step 3 would fold it into the word it times and although Port buffers bars the strobes and flags it is wired to: keep one concept per link direction for the handshake, list each such port under "Enters Through" or "Leaves Through", and hold it at the lines wiring or assigning the port.
  Evidence: cite the lines wiring the port to the FIFO's strobe, or driving it from the flag, as held lines; cite no line assigning the internal strobe or flag as a held line.
- Busy locks.
  Scope: in a unit other than a coprocessor, a flag of this unit, not a port: a register, or a wire decoded from the state register alone.
  Criteria: (1) its value tells whether a multi-step operation of this unit is in progress (set at the start or decoded from the state, cleared at the end); (2) a condition reads it to refuse or delay a write from a request port (a bus or debug-interface record port) into a register of this unit, or to refuse a new command, while it is set.
  Exceptions: not covered: a busy flag read only for a status read-back, for an output port or for the engine's own steps (Sequencing state's busy sub-rule judges it); a flag of a coprocessor (Coprocessor progress state).
  Outcome: a lock (step 2: a lock deciding whether other information may change): it refuses writes while the operation runs. It is a piece of its own, apart from the state it is decoded from, although Sequencing state's busy sub-rule would fold a busy flag decoded from sequencing state into that state: keep one concept for it, and hold it at the line assigning it.
  Evidence: cite the line assigning the flag as its held line, and the lines where it blocks a write as the mechanism.
- Processor control-unit state.
  Scope: the processor unit whose own registers hold the executed instruction word and whose only outputs are a control record port and a register read-back word; never a fetch unit or coprocessor. In it, a signal or record field, never a port: a control or status register that an instruction's register write, a trap entry or a trap return sets, or that a register read returns; the instruction-word, current-address, next-address and return-address registers; a register sampling interrupt inputs, buffering pending interrupts or exceptions, or holding the trap cause; a sleep or trigger-fired flag; a wire deciding whether an instruction or register access is allowed or a buffered interrupt or exception is taken.
  Criteria: (1) it is not the debug-mode flag or trigger start pulse below.
  Exceptions: judged as usual (2.4, 4.4): the debug-mode flag, of any closed-set type, set when entering a trap whose cause marks debug entry, cleared at trap exit, copied unmixed into one port field; the trigger start pulse the dispatch step raises, instead of accepting an instruction, when a hardware trigger matches, read only by the debug-entry request.
  Outcome: it only holds or decides what that port delivers: not a piece of its own, although step 2, step 3, Held outcomes, Processor context fields, 2.4, 4.2 and 4.4 would keep it: keep no concept for it, name it in no concept's information, and cite no line assigning it as a held line. The unit's own ports (its interrupt, fault, wait and done inputs; its output control record), the debug-run flag and the trigger start are judged as usual: keep their concepts and their labels.
- Transfer records.
  Scope: a record port of the unit and its fields; not an Instance-driven record.
  Criteria: (1) the used fields are a transfer's words and only flags timing or qualifying it (valid, ready, acknowledge, error, stalled, width); none is compared with a register number, address or operation code, indexes anything, or carries a mode bit or command (a stored word is none). (2) Input: a valid, ready or acknowledge test lets the whole word into a register (even via a wire) or output port; other fields are only tested, counted, copied into a register, read-back bit or wire feeding one, or wired to a buffer instance's pop input. Output: every field comes from a buffer instance's output or its signal, a slice, multiplexer or bit of one, a decoder instance of this file fed only by such, or constants; selects and conditions read only these, sequencing state, an alignment bit picking which buffered part issues next, or non-record access-command ports.
  Outcome: a transfer's word and handshake, judged as a bus response record port (2.6; section 1): no piece of this unit, although step 1 names data received or returned and responses signalled, and Control record ports would make the port each concept's entry or exit: keep no concept for it, name it in no concept's information, cite none of its lines as held lines. Judged as usual, the port only their entry or exit: the stored word (Forwarded transactions agrees), fault causes, fill flags, addresses, access-command ports.
