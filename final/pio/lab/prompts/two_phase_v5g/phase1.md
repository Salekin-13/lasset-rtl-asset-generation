THIS CALL: PHASE 1, CONCEPTUAL ASSETS

For each UNIT of the diagram:

1. Interface. Name the information entering or leaving through the unit's INPUTS and OUTPUTS: data received, held or returned; settings and configuration; state and status; commands, requests and their responses; events signaled to other modules.

2. Inside. Name state the unit holds that its behavior depends on and no port shows directly: a mode, a lock, a count, a stored setting, a state machine's state. Also name each enable, select, override or lock deciding whether other information is used, passes or may change: such a decision is information of its own.

3. Merge and split. Information that always travels together for the same use, or repeats per index or per port of one role, is one piece. Information with different uses is separate, even on a shared port. An internal signal only timing one step of other information (an increment pulse, a started flag, a one-cycle request) is part of what it times, not a decision of its own. A compare of stored state with a request, a count with a stored limit, or a written value with a fixed value, whose result picks or triggers what happens next, is its own piece (step 2), even when it lasts one cycle. Hold it where it is computed; never merge it into its inputs or the action it triggers. Any other compare, decode or gate is judged by step 2 and the timing clause. A tick only pacing a step is a pacing pulse; a compare only picking a computation's result (a minimum or maximum) is a working value.

4. Rubric. Per piece, answer each question "yes" only when both its parts hold: first, a judgement of what the information is, from what the RTL does with it; second, a mechanism the RTL shows or the black-box rule (section 1) gives.
   Confidentiality. Assume the IP is to be integrated into an IC where confidentiality protections are required. Is this information, received as input or generated inside the IP, something an integrator may consider secret? If the first part holds, can an element of the IP leak or expose it, by holding or carrying it where the integration level can observe it: an output port, a read-back, a debug or test path, a status depending on it, a shared structure, or data-dependent timing (4.4)? Phase 2 judges authorization, so a designed use does not make the second part "no".
   Integrity. Assume the IP is to be integrated into an IC where integrity protections are required. Is this information material an integrator may deem sensitive, or a state or configuration setting that needs to be immutable during certain operations or modes? If the first part holds, can an element of the IP modify it?
   Availability. Does this information gate (enable, block or select) an output port or the use of an input port, or would the IP or the IC stop working without it? If the first part holds, can an element of the IP block, disable or withhold it, so that a port is blocked, a required transfer is lost, or the IP or IC halts?
   Undermined expected behavior. Is this information something that a privileged mode, an override, a bypass, test-packet injection or a similar behavior at the integration level acts on? If the first part holds, can that behavior make the IP produce incorrect output, or stop its function, under normal operation? Focus on what may be compromised.

5. Keep. Keep a piece as a conceptual asset when any question is "yes" AND it passes the asset test (2.3); list the rest under "Not Kept". Phase 2 sees only kept concepts and starts from their held lines.

6. Anchor. List under "Enters Through" each unit port whose value is carried (2.2) into the information, and under "Leaves Through" each unit port written by an element carrying it; either list may be empty. Skip ports that only decide the information or that it only decides. Write ports as INPUTS and OUTPUTS do, or as the closed-set field when one field of a record port alone carries the information.

Rules:
- Describe a conceptual asset by what the information is, not by an element name. A diagram arrow shows a flow, not an asset.
- Clocks and resets. Clock and reset inputs, a reset request that the unit only combines, gates, registers or passes on to a reset chain or reset output port (its copies and that output port included), and chains only synchronizing or releasing a reset (a reset shift register, a registered copy of a reset), are not conceptual assets under any question. The clock line of a serial link that the unit drives to, or senses from, a peer device is not a conceptual asset either, nor is a setting or decision whose only use, apart from a read-back, is to shape that line (its polarity, its phase against the data, or holding it while the peer stretches it), although this rule judges other clock settings as usual. Do not cite their lines as held lines. The link's data and select lines, its rate setting and the unit's clock-enable outputs are judged as usual. Settings or requests controlling a clock (an enable, a rate) are judged as usual, and so is a decision triggering a reset (such as a timeout), where it is computed, except as the next sentence says. A decision that a write was refused or carried a wrong value (a write while locked, a wrong password), its gated or registered copies, and a setting choosing only whether such a violation resets are not conceptual assets either when their only uses, apart from a read-back, are to request a reset and record its cause, although step 3 makes a compare of a written value with a fixed value a piece. The cause record, the lock refusing the write, and a compare outcome that restarts a counter are judged as usual.
- Build-time values. A generic or constant that only fixes the build (a feature switch, a size or depth, a fixed address or address map, a buffering choice) is not a conceptual asset: no element of the IP can change or withhold it at run time. Nor is a run-time bit that a statement ANDs with a build-time switch and whose effect includes writing characters to a file or the screen (a simulation-only mode), although a bus write can change it: it belongs to that build choice and is not the run-time decision the next sentence asks for. Instead, name the run-time decision using it as its own concept (such as which port an address selects, or which requester is granted).
- Pacing pulses. A tick, edge pulse or divider count made inside the unit only to pace another step, or an input port whose only use is a condition letting such a tick or count advance, is part of that step or its rate setting (step 3), unless an output port carries that pulse itself (2.2); an output port that such pulses only decide or time does not count. Do not name it in any concept's information or cite its lines as held lines. A request held until it is served, a start pulse decoded from a received command, and a step counter are not pacing pulses.
- Forwarded transactions. A bus transaction (a request or response with its address, data and handshake) that the unit only forwards between its ports or to a sub-unit, without storing, computing or deciding it, is not a conceptual asset of this unit. Merging the bus responses of several ports into one (an OR or a multiplexer) is still forwarding. So is a register stage that captures a whole request or response record and passes it on unchanged a cycle later, although it stores the record. So is a record this unit only wires between one of its ports and the port map of an instance of another IP, with no statement of this unit reading or writing it (a constant tied to it in a generate branch where the instance is absent is no such statement), even though the black-box rule lets the instance change it; in a unit executing instructions, this does not cover the instructions it executes or the data it loads and stores. The decision whether or where it passes is judged as usual.
- Bus handshake copies. A bus response acknowledge only repeating or delaying the bus request strobe, and a bus error flag tied to a constant, are not information of their own.
- Working values. Partial results inside a computation (a partial sum, product or round value, a synchronizer stage, a debiasing step) are part of the result they produce (step 3), not concepts of their own. So are the state and flag made inside a debiasing step to choose which raw bits it accepts: although step 2 would call them a decision, they only shape that result, like a compare picking a minimum (step 3). Do not name a synchronizer stage in any concept's information or cite its lines as held lines.
- Hand-offs. A wait or fault flag, a write-enable flag, or an access address that one instance outputs on a non-record port and hands to another instance or to this unit's logic is its own piece (step 2), unless Port buffers covers it (then this rule does not apply). No step-3 clause or other rule folds it, even when it travels with the data it qualifies, or when it is only one bit of a count: then hold it at the line assigning that bit to the instance output, and a count kept only to make it belongs to this piece.
- Register read-back. In a unit executing instructions, the word an instance outputs for reads of its control and status registers, when a statement of this unit merges it directly into the value written back to a register, is its own piece: those registers' contents as software reads them. Judge which output that is from port names (section 1's second exception) and say so. Hold it at that instance output. No step-3 clause or other rule folds it, and the read words other instances pass into that instance are not part of it.
- Port buffers. If the write data of a FIFO instance is a unit input port's value (a bus write, or bits shifted in from a serial input port), the FIFO only buffers data between two ports. Then its fill flags (whether it holds data or has room), its push and pop strobes, a command only clearing it, and a flag recording a push while full only time, gate, clear or report on that data: they are not pieces of their own, although step 2 would call some of them a decision. Judged as usual: the buffered data, an output port these flags decide (an interrupt request, a ready-to-receive line), and a unit enable that also clears the FIFO. A FIFO holding data the unit generates itself (random bits) is not covered: its fill flag and its push, pop, clear and enable controls are judged as usual. Judge from port names that an instance is a FIFO and which outputs are its flags, and say so.
- Serial engines. In a unit that shifts data bit by bit onto or off a serial data port, paced by the unit's own rate setting, the engine doing it only decides when that data moves, so it is part of that data and of the enable, not a piece of its own, although step 2 names a state machine's state and a count: its state register, its bit and phase counters, and the busy and done flags made from them. Do not cite their lines as held lines, except a line assigning an element this rule judges as usual. Judged as usual: the data, chip-select and flow-control ports, an interrupt request these flags decide, the enable and rate settings, and the data shift register. Not covered (no such port or rate setting): a unit computing bit by bit from parallel operands, one shifting in bits it generates, and a test or debug access port that the peer's clock paces (4.4).
- Cached copies. In a cache (a unit answering a read from its own copy when a stored tag matches the address, and otherwise fetching the words over a backing bus), the copied words are copies of data the backing memory holds, and the tag and valid bits only record which words are copied: none of them is a piece of this unit, although steps 1 and 2 would name them and 4.4 names caches. Its decisions stay judged as usual: the hit, the bytes a write changes, the address, its fill, clear and invalidate commands, and a pending fence or flush. A memory that is itself the store is judged as usual.
- Operation selectors. In a unit that executes an instruction or an atomic memory operation a processor issues to it (a coprocessor, an atomic read-modify-write), the instruction or request fields that only pick which operation runs or which result form returns (an opcode, a function code, an instruction-type bit), a stored copy of them, and a flag decoded from them that only names the operation are part of that operation (step 3), not pieces of their own, although step 2 names a select. Do not list them under "Enters Through" or cite their lines as held lines, except a line assigning an element this rule judges as usual. Judged as usual: a start command or pulse, even one decoded per operation (a multiply start, a divide start), a register access's address and write enable, a completion flag, and a setting decoded from them that changes how operands are read (such as signedness). A plain bus read or write is not covered: its read or write bit, and a read enable made from it, stay judged as usual.
- Per-region checks. When the unit makes the same compare or permission check per region or entry and only combines the results (a priority chain, an OR) into one decision, that decision is the piece, held where the results combine; the per-region results are its working values (step 3), although step 3 makes a compare of stored state with a request a piece. A per-entry result that itself picks where a request goes or which entry an access changes (which port an address selects, which lock is addressed) stays its own piece.
- Arbitration bookkeeping. A register that only remembers a request's lock flag while that locked sequence lasts, or the previous grant for round-robin priority, serves the grant or transfer monitor that reads it: it is not a piece of its own, even though step 2 names a lock. Do not cite its lines as held lines. Judged as usual: the current grant, its select and its strobe, requests held until served, a reservation, a lock that software sets to guard later accesses, and a timeout count with its suppression flag.
